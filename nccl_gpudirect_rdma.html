NCCL and GPUDirect RDMA

The layer between the RDMA fabric and GPU workloads: what NCCL does, how GPUDirect RDMA moves data, and why PCIe topology decides performance.

1. Why this layer exists

In traditional HPC and EDA workloads, RDMA moves data between host memory on different machines. That is the world the InfiniBand and RoCE page covers.

In GPU workloads such as distributed training and large-model inference, the data that needs to move fastest lives in GPU memory (HBM). A naive path would be: GPU memory → host memory → RDMA to the remote host → remote GPU memory. That adds two copies and CPU involvement to every transfer, which is exactly the overhead RDMA was meant to remove.

GPUDirect RDMA (GDR) removes those hops: the NIC reads and writes directly to and from GPU memory, skipping host memory. NCCL (NVIDIA Collective Communications Library) sits on top and decides which GPUs talk to which, using GDR as the transport when it is available.

The one model to keep: NCCL is the "what to communicate" layer, GPUDirect RDMA is the "how it physically moves" layer, and IB or RoCE is the fabric under both.

2. NCCL fundamentals

What it does

NCCL implements collective communication primitives, the patterns distributed training actually needs:

Primitive What it does Typical use
AllReduce Combines (for example, sums) data across all GPUs and returns the result to all of them Gradient synchronization in data-parallel training, the most common operation
Broadcast Sends one GPU's data to all others Distributing initial model weights
AllGather Collects each GPU's data and shares it with every GPU Assembling sharded data in tensor or model parallelism
ReduceScatter Combines data, then splits the result across GPUs Paired with AllGather in optimized AllReduce and in sharded-optimizer training (ZeRO, FSDP)

Topology awareness

At startup NCCL detects how GPUs are connected: NVLink between GPUs in the same host, the PCIe tree, and which NICs sit closest to which GPUs. It then picks ring or tree patterns that respect that layout. This is the same "locality matters" principle as fabric-aware job placement, one level down.

Operational implication: an asymmetric PCIe/NIC layout (for example, a GPU whose nearest NIC is on a different root complex) slows NCCL down without raising errors. It is a common source of "this cluster benchmarks worse than it should" tickets.

Key variables and tools

Variable / tool Purpose
NCCL_DEBUG=INFO NCCL's diagnostic logging, the first thing to turn on for any multi-node issue. Look for GDRDMA in the transport lines to confirm GDR is in use.
NCCL_IB_HCA Pins which HCAs NCCL uses, important on multi-NIC nodes
NCCL_SOCKET_IFNAME Interface for NCCL's bootstrap and control traffic (non-RDMA)
NCCL_NET_GDR_LEVEL How close GPU and NIC must be (in PCIe terms) before NCCL uses GDR instead of host-staged copies
nccl-tests NVIDIA's benchmark suite (all_reduce_perf and friends) for validating a new or suspect segment, the GPU counterpart of ib_write_bw

3. GPUDirect RDMA mechanics

What makes it possible

The NIC's DMA engine is given direct access to GPU memory over PCIe peer-to-peer, so data moves between NIC and GPU without the CPU or host RAM in the path. On Linux this requires the nvidia-peermem kernel module (the older out-of-tree module was nv_peer_mem), or DMA-BUF support in newer driver and kernel combinations.

Why PCIe topology decides performance

GDR performance depends heavily on whether the GPU and its NIC sit under the same PCIe switch, or whether traffic has to cross the root complex or, worse, the inter-socket link (QPI/UPI). That is why GPU servers built for this work (NVIDIA HGX/DGX-class systems and equivalents) pair each GPU with a NIC on a shared PCIe switch. nvidia-smi topo -m shows the relationship: PIX or PXB between a GPU and NIC is good; SYS means traffic crosses sockets.

Common failure and degradation modes

Symptom Likely cause
Throughput far below expected, no errors GDR not engaged and NCCL silently falling back to host-staged copies. Check NCCL_DEBUG=INFO for the transport chosen, and confirm lsmod | grep nvidia_peermem.
Inconsistent performance across identical nodes Asymmetric PCIe topology, or BIOS differences (ACS or IOMMU settings blocking peer-to-peer) on some nodes
Job hangs at NCCL init Usually fabric or network: check port state, then error counters, then fabric-wide state (SM or DCB) before suspecting training code
Works on one node, fails across nodes Almost always the fabric (IB/RoCE misconfiguration) or a firewall blocking NCCL's bootstrap traffic, not NCCL or the model code

4. What carries over from fabric operations

The diagnostic discipline doesn't change: rule out config, check local hardware and port state, check error counters, check fabric-wide state, and only then suspect the application. What's new is:

  • One more layer below the fabric to be aware of (PCIe and NVLink topology)
  • A few more tools (NCCL_DEBUG, nccl-tests, nvidia-smi topo -m) alongside ibstat, mlxlink, and ethtool
  • One new mental model (collectives) that explains why the traffic pattern looks the way it does

Before production: check environment variable names and defaults against NVIDIA's current NCCL documentation, since they change between releases.
