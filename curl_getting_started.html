This is a gentle introduction. Each step teaches one idea, shows the command, shows what you should see, and explains the pieces. You don't need to memorize anything. By the end you'll know a pattern that works on almost every monitoring tool.

When you want the full details later, the complete reference and the cheat sheet are there.

What you need: a Linux machine that can reach your Prometheus server, plus curl and jq.

sudo dnf install -y curl jq

Throughout this guide, replace localhost with your monitoring server's name if you're running the commands from another machine. Sample outputs are trimmed and your numbers will differ.

The one idea behind all of this

Monitoring tools like Prometheus, Grafana and Loki are web servers. They don't serve web pages for people, though. They answer questions for other programs over HTTP.

curl lets you ask those same questions from the command line. Almost every tool answers three kinds of question:

Question Typical address
Are you alive? /-/healthy, /ready, /api/health
What are your numbers? /metrics
Can you answer my query? /api/v1/...

Once you've seen this pattern a couple of times, you'll recognize it everywhere.

Step 1: Ask Prometheus if it's alive

Why: This is the simplest possible question, so it's the first thing you check when something seems broken.

curl http://localhost:9090/-/healthy

What you'll see:

Prometheus Server is Healthy.

That's it. You sent a request and Prometheus answered in plain text.

Try the "ready" version too. "Healthy" means the program is running. "Ready" means it has finished starting up and can answer queries.

curl http://localhost:9090/-/ready

Prometheus Server is Ready.

Step 2: Get just the status code

Why: In scripts you usually don't care about the text. You only want to know whether it worked. Web servers report that with a three-digit status code: 200 means OK, 404 means not found, 500-something means the server had a problem.

curl -s -o /dev/null -w '%{http_code}\n' http://localhost:9090/-/ready

What you'll see:

200

What the pieces mean:

  • -s stands for silent. It hides curl's progress meter.
  • -o /dev/null throws the response body away.
  • -w '%{http_code}\n' prints the status code, followed by a newline.

Step 3: When it doesn't work, look closer with -v

Why: "It doesn't work" can mean many different things. -v (verbose) shows each stage of the conversation, so you can see where it stops.

curl -v http://localhost:9090/-/ready

What you'll see (trimmed):

*   Trying 127.0.0.1:9090...
* Connected to localhost (127.0.0.1) port 9090
> GET /-/ready HTTP/1.1
> Host: localhost:9090
>
< HTTP/1.1 200 OK
< Content-Type: text/plain; charset=utf-8
<
Prometheus Server is Ready.

How to read it:

  • Lines starting with * are curl describing what it's doing.
  • Lines starting with > are what you sent.
  • Lines starting with < are what the server sent back.

Common failures and what they mean:

You see It usually means
Connection refused Nothing is listening on that port. The service is down, or it's listening on a different address.
It hangs, then Connection timed out Something is blocking the traffic, usually a firewall.
HTTP/1.1 401 or 403 The server is up but wants a login or token.
HTTP/1.1 404 Wrong address (path), or the feature isn't turned on.

Step 4: Look at raw metrics

Why: Prometheus collects numbers by visiting a /metrics page on each machine, which it calls "scraping." node_exporter is the program that publishes those numbers for a Linux server. If you can read the page with curl, Prometheus can too.

curl -s http://node01:9100/metrics | head -20

What you'll see (trimmed):

# HELP node_load1 1m load average.
# TYPE node_load1 gauge
node_load1 0.42
# HELP node_memory_MemAvailable_bytes Memory information field MemAvailable_bytes.
# TYPE node_memory_MemAvailable_bytes gauge
node_memory_MemAvailable_bytes 1.2345e+11

How to read it: each measurement comes in three lines.

  • # HELP is a plain-English description.
  • # TYPE says what kind of number it is. A gauge goes up and down, like temperature. A counter only goes up, like total bytes sent.
  • The last line is the name and the current value.

Some lines have labels in curly braces. Labels tell apart several versions of the same measurement:

node_filesystem_avail_bytes{mountpoint="/"} 5.1e+10
node_filesystem_avail_bytes{mountpoint="/scratch"} 8.7e+12

The pipe | head -20 just shows the first 20 lines, because the full page is long.

Step 5: Find the one number you care about

Why: The metrics page has hundreds of lines. grep filters it down.

curl -s http://node01:9100/metrics | grep '^node_load'

node_load1 0.42
node_load15 0.38
node_load5 0.40

The ^ means "starting with," so this skips the # HELP and # TYPE lines.

Step 6: Talk to an API and make the answer readable

Why: The /metrics page is plain text. The API, the address where you ask questions, answers in JSON: structured text that programs read easily but people don't. jq makes it readable.

First, without jq:

curl -s http://localhost:9090/api/v1/status/buildinfo

{"status":"success","data":{"version":"3.5.0","revision":"...","branch":"HEAD","buildUser":"...","goVersion":"go1.24.4"}}

Now pipe it through jq .:

curl -s http://localhost:9090/api/v1/status/buildinfo | jq .

{
  "status": "success",
  "data": {
    "version": "3.5.0",
    "goVersion": "go1.24.4"
  }
}

The . means "show me everything, nicely laid out."

Step 7: Pick out just the part you need

Why: Usually you want one value, not the whole answer. jq can walk into the JSON for you.

curl -s http://localhost:9090/api/v1/status/buildinfo | jq -r '.data.version'

3.5.0

What the pieces mean:

  • .data.version means "go into data, then take version."
  • -r means "raw": print the text without quotation marks.

Tip: when you don't know what's inside an answer, jq 'keys' lists the top-level names, and you can explore from there.

Step 8: Ask Prometheus a question

Why: This is where it gets useful. Prometheus has its own question language called PromQL. The simplest question is up: "for every machine you scrape, could you reach it?" 1 means yes and 0 means no.

curl -sG http://localhost:9090/api/v1/query --data-urlencode 'query=up'

What the new pieces mean:

  • -G puts the question into the web address, the way a browser search does.
  • --data-urlencode 'query=up' packages the question safely. PromQL is full of characters like {, " and spaces that would break a web address, and this flag handles them for you. Always use it for queries. It prevents the most common beginner error, bad_data: parse error.

The raw answer is long JSON. Let's make it a simple list:

curl -sG http://localhost:9090/api/v1/query --data-urlencode 'query=up' \
  | jq -r '.data.result[] | "\(.metric.instance)  \(.value[1])"'

node01:9100  1
node02:9100  1
node03:9100  0
localhost:9090  1

node03 is down. You found that without opening Grafana.

The jq part looks scary, but it says something simple: "for each result, print the instance name, two spaces, then the value."

Now ask only for what's broken:

curl -sG http://localhost:9090/api/v1/query --data-urlencode 'query=up == 0' \
  | jq -r '.data.result[].metric.instance'

node03:9100

Step 9: Ask Prometheus why something is down

Why: up == 0 tells you what is broken. The targets page tells you why.

curl -s http://localhost:9090/api/v1/targets \
  | jq -r '.data.activeTargets[] | select(.health != "up") | "\(.scrapeUrl)  ->  \(.lastError)"'

http://node03:9100/metrics  ->  Get "http://node03:9100/metrics": dial tcp 10.1.1.13:9100: connect: connection refused

select(.health != "up") keeps only the unhealthy targets. "connection refused" points you to Step 3's table: node_exporter isn't running on node03.

Confirm it yourself from the Prometheus server:

curl -v http://node03:9100/metrics

Step 10: Send something, not just ask

Why: So far you've only read data. That's a GET request. Sending data is a POST. A safe way to practice is a fake alert sent to Alertmanager, which is the tool that sends you email or chat notifications. It also proves your alert routing works.

curl -s -X POST http://localhost:9093/api/v2/alerts \
  -H 'Content-Type: application/json' \
  -d '[{"labels": {"alertname": "PracticeAlert", "severity": "info"},
        "annotations": {"summary": "Just testing curl - safe to ignore"}}]'

What the pieces mean:

  • -X POST means "I'm sending, not asking."
  • -H 'Content-Type: application/json' adds a header, a note that tells the server the data is JSON.
  • -d '...' is the data itself.

Now check that it arrived:

curl -s http://localhost:9093/api/v2/alerts | jq -r '.[].labels.alertname'

PracticeAlert

It disappears on its own after a few minutes.

Step 11: Use a login token (Grafana)

Why: Some tools want to know who you are. Grafana uses a token, a long secret string you create once in the Grafana UI under Administration → Service accounts.

Store it in a file so it doesn't end up in your shell history:

echo 'glsa_your_token_here' > ~/.grafana_token
chmod 600 ~/.grafana_token

Then send it as a header:

curl -s -H "Authorization: Bearer $(cat ~/.grafana_token)" \
  http://localhost:3000/api/search?type=dash-db | jq -r '.[].title'

Node Exporter Full
Slurm Cluster Overview
GPU Utilization

That's a list of your dashboards. The same pattern, a header carrying a token, works with most tools that need a login.

Step 12: Turn it into a simple check script

Why: Once a command is useful, you'll want to run it on a schedule. Scripts need to know whether something failed, and -f (fail) makes curl report errors through its exit code.

curl -fsS http://localhost:9090/-/ready && echo "Prometheus OK" || echo "Prometheus PROBLEM"
  • -f makes curl exit with an error when the server returns an error code (400 or higher).
  • -S still shows the error message, even with -s.
  • && ... || ... means "if it worked, say OK; otherwise, say PROBLEM."

A tiny script that checks several services:

#!/usr/bin/env bash
for url in \
  http://localhost:9090/-/ready \
  http://localhost:9093/-/ready \
  http://localhost:3000/api/health \
  http://localhost:3100/ready
do
  if curl -fsS --max-time 5 -o /dev/null "$url"; then
    echo "OK    $url"
  else
    echo "FAIL  $url"
  fi
done

--max-time 5 gives up after 5 seconds, so a frozen service can't hang your script.

What you've learned

You now know the whole pattern:

  1. Is it alive? curl URL/-/ready (or /ready, /api/health)
  2. What does it say? curl -s URL | jq .
  3. Just the part I need: | jq -r '.path.to.value'
  4. Ask a question: curl -sG URL --data-urlencode 'query=...'
  5. Why doesn't it work? curl -v URL
  6. Send something: curl -X POST -H 'Content-Type: application/json' -d '...'
  7. Log in: -H "Authorization: Bearer TOKEN"
  8. Use it in a script: curl -fsS --max-time 5

Those eight lines cover most of what you'll do day to day.
