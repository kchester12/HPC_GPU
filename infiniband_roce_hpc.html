InfiniBand and RoCE for HPC Schedulers

How the two RDMA fabrics differ, where they fail, and how to make LSF (and Slurm) fabric-aware.

1. Why RDMA fabrics exist

Both InfiniBand and RoCE solve the same problem: standard TCP/IP networking is too slow and too CPU-hungry for tightly coupled HPC workloads such as large MPI jobs, distributed training, and tightly synchronized emulation runs.

The fix is RDMA (Remote Direct Memory Access): one server's NIC writes directly into another server's memory, bypassing the kernel, the TCP/IP stack, and almost all CPU involvement. That gives you:

  • Low single-digit microsecond latency, versus tens of microseconds for a TCP round trip through the kernel stack
  • Near-zero CPU overhead for data movement, because the NIC does the work
  • High sustained bandwidth with minimal jitter

InfiniBand is a purpose-built RDMA fabric with its own physical layer, switches, and management protocol.

RoCE (RDMA over Converged Ethernet) carries the same RDMA verbs over Ethernet, so you get RDMA-class performance on Ethernet switches, cabling, and tooling your team already knows.

At the application layer they are not competing technologies. An MPI job calling RDMA verbs doesn't fundamentally care whether IB or RoCE is underneath. The differences are in the fabric, management, and failure modes, which is exactly where an HPC operations engineer works.

2. InfiniBand architecture

Physical and link layer

  • Dedicated IB switches and HCAs (Host Channel Adapters), not shared with general Ethernet traffic.
  • Link speeds named by generation: SDR, DDR, QDR, FDR, EDR, HDR, NDR, XDR, with throughput rising each generation.
  • Usually deployed in a fat-tree (Clos) topology, because non-blocking or near-non-blocking bisection bandwidth is the whole point.

The Subnet Manager: the defining IB concept

This is the biggest conceptual difference from Ethernet.

  • IB has no flooding, MAC learning, or spanning tree. A Subnet Manager (usually OpenSM, or a vendor SM such as NVIDIA UFM) discovers the fabric topology and assigns LIDs (Local Identifiers) and routes to every port.
  • The SM runs on a host or a managed switch and must be highly available. Fabrics normally run a master plus standby SMs with election. SM failover is a classic operational risk.
  • Routing tables, partition keys (P_Keys, IB's VLAN-like segmentation), and QoS policies are all pushed out by the SM.
  • Operational implication: an IB fabric problem is very often an SM problem (stale routing, failover storms, P_Key misconfiguration) rather than a cable or card fault.

3. RoCE architecture

RoCE v1 vs RoCE v2

  • RoCE v1: RDMA encapsulated directly in Ethernet frames (layer 2 only). Not routable and rarely used today.
  • RoCE v2: RDMA encapsulated in UDP/IP (port 4791), so it is routable. Essentially all modern deployments, including ConnectX-6 Lx environments, use v2.

The catch: Ethernet must be made lossless

Standard Ethernet drops packets under congestion and relies on TCP to retransmit. RDMA tolerates loss poorly, so RoCE needs lossless or near-lossless Ethernet, built from:

  • PFC (Priority Flow Control, IEEE 802.1Qbb): pauses specific traffic classes, not the whole link, when a receive buffer fills, instead of dropping.
  • ECN with DCQCN (Data Center Quantized Congestion Notification): proactive congestion signaling so senders back off before PFC pauses are needed. DCQCN is the standard RoCE v2 congestion-control algorithm.
  • DCB (Data Center Bridging): the switch feature set (PFC, ETS, DCBX) that must be configured correctly and consistently on every hop. Inconsistency here is by far the most common source of RoCE production incidents.

Operational implication: RoCE stability problems are disproportionately switch QoS/DCB misconfiguration. A single hop with PFC or ECN settings that don't match the rest of the fabric is a classic cause of silent degradation: throughput drops or micro-stalls appear with no obvious link errors.

Key RoCE tools

Tool Purpose
ethtool -S <iface> NIC counters, including pause frames and RoCE-relevant drops on NVIDIA/Mellanox NICs
mlxconfig / mlxlink ConnectX firmware configuration and link diagnostics

4. Side by side

Dimension InfiniBand RoCE v2
Fabric Dedicated IB switches Ethernet switches with DCB/PFC/ECN support
Routing and management Centralized Subnet Manager (OpenSM/UFM) Standard IP routing plus switch QoS config
Loss handling Credit-based flow control in the link layer PFC plus ECN/DCQCN, configured end to end

5. Making the scheduler fabric-aware

Why the scheduler needs to know about the fabric

For tightly coupled MPI and emulation workloads, where a job's ranks land relative to each other matters as much as raw node availability. Ranks under the same leaf switch communicate faster than ranks that cross the spine, so topology-aware placement is a real performance lever.

LSF mechanisms

  • Compute units. Define your leaf switches or racks as compute units (COMPUTE_UNIT_TYPES in lsb.params, members in lsb.hosts). Jobs can then request locality with bsub -R "cu[type=switch:maxcus=1]", or use span[] to control how slots spread across hosts.
  • Pre-execution health checks. A queue-level PRE_EXEC (or bsub -E) runs on the selected execution host before the job starts. Check HCA/port state and error counters there; a non-zero exit makes LSF requeue the job instead of letting it fail at MPI init. (esub runs at submission time, before a host is chosen, so it suits request validation rather than per-host fabric checks.)
  • elim scripts. An external LIM can report custom fabric-health resources (port state, error counters, link speed) into LSF's load information, so hosts with a bad fabric link can be excluded through resource requirements or closed automatically. This is the same pattern as feeding any other hardware health into an elim.

Slurm equivalents

  • topology.conf with TopologyPlugin=topology/tree describes the switch hierarchy, and --switches=N@max-wait asks for a job to land under a limited number of leaf switches.
  • Prolog and HealthCheckProgram (often NHC) can check HCA state and drain nodes with fabric faults.

The diagnostic order for fabric-suspect failures

Job failures that look like "random MPI init failures" or "hangs at startup" are very often fabric-layer problems: a bad HCA, a marginal cable, SM routing that hasn't converged, or RoCE congestion. Once scheduler configuration is ruled out, investigate in this order:

  1. Local HCA and port state on the hosts involved (ibstat, mlxlink, ethtool -S).
  2. Error counters: symbol errors, link flaps, PFC pause counts, ECN-marked packets.
  3. Fabric-wide state: SM logs and routing recalculations (IB), or DCB config consistency across every hop (RoCE).
  4. Workload pattern: is it correlated with job size, rank count, or time of day (congestion)?
  5. Only after all of that, treat it as an application or scheduler bug.

Before production: verify tool syntax and PFC/DCQCN configuration against your NIC and switch vendor documentation.
