From sbatch to REST: API-Driven Slurm Jobs

Why and how to submit and monitor Slurm jobs through slurmrestd: the mental shift, CLI-to-API mapping, a curl walkthrough, monitoring models, and staging test case data.

A REST API doesn't replace sbatch. It's a second front door to the same scheduler, built for programs rather than people. If you've spent years at a shell prompt, it's natural to wonder why anyone would want it. This guide explains the mental shift, maps the commands you already know to their API equivalents, and walks through submitting and monitoring a job with curl.

1. Why this feels foreign

The interactive world is built around a person at a terminal. You SSH to a login node, write a batch script, run sbatch, glance at squeue, and read slurm-12345.out when it finishes. Every step assumes four things:

  • A human is present. You read the output, notice the error, decide what to do next.
  • You are logged in. You have a Unix account, a home directory, and a shell on a cluster node.
  • Output is text for eyes. squeue prints columns lined up for a terminal, not for a parser.
  • State lives in your head. You remember which job IDs belong to which experiment, or keep notes.

That model works very well for one person running jobs. It becomes awkward as soon as something other than a person needs to run jobs: a web portal, a workflow engine like Nextflow, a CI pipeline, a dashboard, or another team's application that has no business holding a shell account on your cluster.

The API world assumes the client is a program. A program doesn't SSH anywhere or read columns. It sends a structured request over the network ("run this script, with these resources") and gets a structured answer back ({"job_id": 12345}). Later it asks "what's the state of 12345?" and gets {"job_state": ["COMPLETED"], "exit_code": ...}. There's no screen scraping and no guessing.

Why it doesn't click at first:

What HPC users expect What the API gives them Why it feels wrong
Type a command, see a result Send JSON, get JSON back More typing for the same job; the payoff isn't visible yet
sbatch reads my script from disk The script travels inside the request as a string "Why would I put my script inside a JSON blob?"
Environment is inherited from my shell Environment must be stated explicitly Jobs fail because PATH was never set
Login proves who I am A token proves who I am on every request Tokens feel like extra ceremony
I watch the job Something must poll or be notified There's no terminal to watch

The key point: if you are the client, the CLI is better. If a program is the client, the API is better. Most of the confusion goes away once people stop asking "is this better than sbatch for me?" and ask "what's the best way for software to talk to the scheduler?"

A useful comparison: you don't use a REST API to check your bank balance, you use the app. But the app itself uses the bank's API. In HPC, Open OnDemand, workflow managers and portals are the "app". The REST API is what they should be built on instead of shelling out to sbatch and parsing its text.

2. Same scheduler, new front door

slurmrestd is a small daemon that ships with Slurm. It listens for HTTP requests (port 6820 by default) and turns them into the same calls sbatch, squeue and scontrol make to slurmctld. For accounting, it talks to slurmdbd, just like sacct. Nothing about scheduling changes: same partitions, same QOS, same fairshare, same limits, same job IDs. A job submitted through the API shows up in squeue like any other.

  You at a shell ──── sbatch / squeue / scontrol ────┐
                                                      ├──►  slurmctld  ──►  compute nodes
  A program ──── HTTPS + JSON ──►  slurmrestd ────────┤
                                                      └──►  slurmdbd   (sacct / accounting)

Commands you know, and their API equivalents. V is the API version your Slurm supports (for example v0.0.42; find yours with slurmrestd -d list).

You type today REST call What comes back
sbatch job.sh POST /slurm/V/job/submit job_id
squeue GET /slurm/V/jobs every active job, as JSON
squeue -j 12345 / scontrol show job 12345 GET /slurm/V/job/12345 one job's full record
scancel 12345 DELETE /slurm/V/job/12345 success or error
scontrol update jobid=12345 ... POST /slurm/V/job/12345 success or error
sinfo / scontrol show nodes GET /slurm/V/nodes every node's state, CPUs, memory, GRES
sinfo -s (partitions) GET /slurm/V/partitions partition definitions and limits
sdiag GET /slurm/V/diag scheduler statistics
scontrol ping GET /slurm/V/ping controller up/down
sacct -j 12345 GET /slurmdb/V/job/12345 finished job: state, exit code, usage
sacct -S ... GET /slurmdb/V/jobs?start_time=... historical jobs
sacctmgr show assoc GET /slurmdb/V/associations accounts, users, limits

The whole API is described in an OpenAPI spec that slurmrestd serves itself at /openapi/v3. Tools can generate client libraries from it, and you can browse it to find any endpoint.

Three differences that trip people up:

  1. The script travels in the request. sbatch reads job.sh from disk. The API receives the script's text as a string inside the JSON ("script": "#!/bin/bash\n..."). #SBATCH lines inside it still work, but options are usually given as JSON fields instead.
  2. No inherited environment. sbatch copies your shell's environment into the job. slurmrestd has no shell to copy from, so you must pass at least PATH. This is the number-one cause of "my API job fails but sbatch works."
  3. Output files don't come back in the response. The job still writes slurm-%j.out to the shared filesystem. The API tells you that the job finished and its exit code; reading the output is a separate step (see section 8).

3. What's in it for me?

The honest answer: for a researcher submitting a few jobs by hand, very little. The benefits show up when software submits jobs, when many jobs need tracking, or when people who shouldn't have shell access need to run work.

For researchers and workflow users

  • No more parsing squeue text. Scripts that do squeue | awk '{print $5}' break when someone changes SQUEUE_FORMAT or Slurm changes a column. JSON fields have names, so .job_state is .job_state regardless of formatting.
  • Submit from anywhere. A laptop, a Jupyter notebook, or a lab instrument PC can submit and track jobs over HTTPS without an interactive SSH session, as long as it's allowed to reach slurmrestd.
  • Exact job IDs and states, every time. sbatch prints Submitted batch job 12345 and your script greps the number out. The API returns {"job_id": 12345}.
  • Workflow engines get sturdier. Tools like Nextflow, Snakemake and Cromwell traditionally wrap sbatch/squeue/sacct and parse text. Polling squeue for thousands of tasks is one of the classic ways a workflow hammers slurmctld. A proper API client can ask for exactly the jobs it cares about.

For admins

  • Portals without shell accounts on login nodes. A web front end (a self-service portal, an EDA regression dashboard, a vendor tool) can submit as the user through a token instead of SSH-ing in and screen-scraping.
  • Monitoring and dashboards get real data. Node states, partition load, scheduler stats from /diag, and job counts come straight out as JSON. That's much easier to feed into Prometheus or Grafana than parsing sinfo.
  • One audited, controllable entry point. Every API request carries a token tied to a user, with a lifetime you set. You can put slurmrestd behind a reverse proxy with TLS, rate limits and access logs. It's easier to reason about than "any script that can SSH to a login node."
  • Automation for your own work. Draining nodes before BMC maintenance, resuming them after, and checking scheduler health from a cron job or Ansible playbook can all be HTTP calls with structured results.

For the organization

  • HPC becomes a service other teams can build on. A CI system can run a nightly regression on the cluster. A data pipeline can launch post-processing when files land. A Veloce emulation flow can queue its compile and run stages and report status into a dashboard. None of them needs to know how to SSH to a login node.
  • It matches how the rest of IT works. OpenStack, Kubernetes, storage arrays and BMCs (Redfish) are all driven by REST APIs. Slurm joining that model means the same tooling, skills and security patterns apply.

When the CLI is still the better tool

Situation Use
You're at a terminal, submitting and checking your own jobs sbatch / squeue (faster, simpler, inherits your environment)
Interactive work: srun --pty, salloc, debugging on a node CLI only; the API has no interactive sessions
Quick one-off admin checks sinfo, scontrol
A program, portal, pipeline or dashboard talks to Slurm REST API
Monitoring many jobs or the whole cluster from code REST API (or an exporter, see section 5)
Users who shouldn't have shell access must run jobs REST API behind a portal

Tell users this plainly: the API is not a replacement for what they do today. It's the right tool once the thing submitting jobs is software.

4. Walkthrough: a job's whole life with curl

This walkthrough mirrors what you'd do with sbatch, squeue, sacct and scancel, one step at a time. It assumes slurmrestd is running with JWT auth enabled (section 7). JSON field names have shifted between API versions, so treat these as a pattern and check your version's spec when something doesn't match.

Step 0: Set up your session

export SR=http://head01:6820          # where slurmrestd listens
export V=v0.0.42                      # your API version: slurmrestd -d list
unset SLURM_JWT; export $(scontrol token lifespan=3600)   # sets SLURM_JWT for one hour

scontrol token asks Slurm for a token proving who you are. Tokens expire after 30 minutes by default, so lifespan sets a longer life. Think of it as a hotel room key: limited, temporary, and tied to you.

Put the headers in a reusable variable so every call carries them:

AUTH=(-H "X-SLURM-USER-NAME: $USER" -H "X-SLURM-USER-TOKEN: $SLURM_JWT")

Step 1: Is the scheduler there? (like scontrol ping)

curl -s "${AUTH[@]}" $SR/slurm/$V/ping | jq '.pings'

[ { "hostname": "head01", "pinged": "UP", "mode": "primary" } ]

If you get HTTP 401 or 500 instead, your token is missing or expired. Run the scontrol token line again.

Step 2: Describe the job (like writing job.sh)

With sbatch, your options live in #SBATCH lines. Here they're JSON fields, and the script itself is a string:

cat > job.json <<EOF
{
  "job": {
    "name": "rest-hello",
    "partition": "compute",
    "account": "hpc",
    "tasks": 1,
    "cpus_per_task": 2,
    "memory_per_node": { "set": true, "number": 2048 },
    "time_limit": { "set": true, "number": 10 },
    "current_working_directory": "$HOME/rest-demo",
    "standard_output": "$HOME/rest-demo/rest-hello-%j.out",
    "environment": [ "PATH=/usr/local/bin:/usr/bin:/bin", "HOME=$HOME" ],
    "script": "#!/bin/bash\necho Hello from \$(hostname)\nsleep 60\necho done"
  }
}
EOF
mkdir -p $HOME/rest-demo

How it lines up with what you know:

#SBATCH line JSON field
--job-name=rest-hello "name": "rest-hello"
--partition=compute "partition": "compute"
--ntasks=1 --cpus-per-task=2 "tasks": 1, "cpus_per_task": 2
--mem=2G "memory_per_node": {"set": true, "number": 2048} (MB)
--time=10 "time_limit": {"set": true, "number": 10} (minutes)
--output=... "standard_output": "..."
(inherited environment) "environment": [...], which you must set

The {"set": true, "number": N} wrapper is how newer API versions say "this value was given" as opposed to "use the default." Older versions put "script" at the top level, beside "job"; current ones accept it inside "job".

Step 3: Submit (like sbatch)

JOBID=$(curl -s "${AUTH[@]}" -H 'Content-Type: application/json' \
  --data-binary @job.json $SR/slurm/$V/job/submit | tee submit.json | jq -r '.job_id // .result.job_id')
echo "submitted $JOBID"

submitted 48213

If JOBID is empty or null, look at the errors array in submit.json. It's the API's version of the error sbatch prints:

jq '.errors' submit.json

Slurm still applies every rule it always does: partition limits, QOS, your account association, job_submit plugins.

Step 4: Watch it (like squeue -j)

curl -s "${AUTH[@]}" $SR/slurm/$V/job/$JOBID | jq '.jobs[0] | {job_id, name, job_state, nodes, start_time: .start_time.number}'

{ "job_id": 48213, "name": "rest-hello", "job_state": ["RUNNING"], "nodes": "node017", "start_time": 1763398812 }

Notice that job_state is a list. A job can carry several flags at once, for example ["PENDING", "REQUEUED"]. And squeue still sees it:

squeue -j $JOBID

A simple polling loop, the API version of watching squeue:

while :; do
  STATE=$(curl -s "${AUTH[@]}" $SR/slurm/$V/job/$JOBID | jq -r '.jobs[0].job_state | join(",")')
  echo "$(date +%T) $STATE"
  case $STATE in PENDING*|RUNNING*|CONFIGURING*|COMPLETING*) sleep 15 ;; *) break ;; esac
done

Fifteen seconds is plenty. Polling every second from many clients adds load to slurmctld, exactly like a watch -n1 squeue habit.

Step 5: Get the result (like sacct)

Once a job finishes, it leaves slurmctld's memory after MinJobAge (300 seconds by default). Accounting in slurmdbd is the permanent record:

curl -s "${AUTH[@]}" $SR/slurmdb/$V/job/$JOBID | jq '.jobs[0] | {job_id, state: .state.current, exit_code, elapsed: .time.elapsed, nodes}'

{ "job_id": 48213, "state": ["COMPLETED"], "exit_code": { "status": ["SUCCESS"], "return_code": { "set": true, "number": 0 } }, "elapsed": 61, "nodes": "node017" }

The output itself is on the shared filesystem, just as with sbatch:

cat $HOME/rest-demo/rest-hello-$JOBID.out

Step 6: Cancel (like scancel)

curl -s "${AUTH[@]}" -X DELETE $SR/slurm/$V/job/$JOBID | jq '.errors'

An empty errors list means it worked.

Bonus: the cluster view (like sinfo)

curl -s "${AUTH[@]}" $SR/slurm/$V/nodes |
  jq -r '.nodes[] | "\(.name)\t\(.state | join(","))\t\(.alloc_cpus)/\(.cpus) CPUs"' | column -t

node017  ALLOCATED  32/32 CPUs
node018  IDLE       0/32 CPUs
node019  DOWN,DRAIN 0/32 CPUs

5. Monitoring models: how a program "watches" jobs

At a terminal, you watch jobs with your eyes. A program needs a strategy. There are four, and real systems usually combine two of them.

Model How it works Good for Watch out for
Polling the live API Ask GET /job/{id} or GET /jobs every N seconds Portals, workflow engines tracking their own jobs Load on slurmctld if many clients poll fast
Querying accounting Ask slurmdbd (/slurmdb/V/jobs) for finished jobs Final state, exit codes, usage reports, chargeback Not real-time; jobs appear after they end or change state
Metrics (pull) An exporter turns scheduler state into Prometheus metrics; Grafana graphs them Cluster-wide trends: queue depth, utilization, pending reasons Not per-job tracking; you see counts, not individual jobs
Events (push) Slurm tells you when something happens Reacting immediately to job end or node failure Slurm has no general webhook; you build it from the pieces below

Polling, done politely

Polling is the model most people start with, and it's fine if you're considerate:

  • Ask for many jobs in one call. One GET /slurm/V/jobs every 30 seconds beats 500 separate GET /job/{id} calls. Filter in your code.
  • Use update_time. GET /slurm/V/jobs?update_time=<epoch> returns only jobs that changed since then, which keeps responses small.
  • Back off. Poll pending jobs slowly (60 seconds or more) and running jobs moderately (15–30 seconds). Stop polling once a job reaches a final state.
  • Fall back to accounting. If GET /job/{id} stops finding the job, it has aged out of slurmctld (MinJobAge). Ask /slurmdb/V/job/{id} for the final answer.

Here's the life of a job as a poller sees it, and which source holds the truth at each stage:

 submit ──► PENDING ──► RUNNING ──► COMPLETING ──► COMPLETED / FAILED / TIMEOUT / CANCELLED
            │                                        │
            └── live API: /slurm/V/job/{id} ───────┘── (gone after MinJobAge)
                                                     │
                          accounting: /slurmdb/V/job/{id} ──── permanent record

Metrics: the cluster-wide picture

For dashboards, don't poll per job. Run a Slurm Prometheus exporter that queries Slurm periodically and exposes metrics such as jobs pending or running per partition, nodes by state, and CPU/GPU allocation. Prometheus scrapes it, and Grafana graphs and alerts on it. Several community exporters exist; newer ones read from slurmrestd instead of parsing squeue/sinfo, which is lighter on the controller.

# same curl pattern as any exporter
curl -s http://head01:<exporter-port>/metrics | grep -E '^slurm_(jobs|nodes|partition)' | head

Events: getting told instead of asking

Slurm doesn't call a URL when a job finishes, but you can build that behavior from parts it does have:

  • Job completion plugins. JobCompType=jobcomp/elasticsearch or jobcomp/kafka sends a record of every finished job to Elasticsearch or a Kafka topic. Downstream tools subscribe instead of polling.
  • An epilog or the job itself. The last line of a job script can curl -X POST a webhook, such as a chat channel, your portal, or Alertmanager (see the observability guide). This is the simplest "tell me when it's done" hook.
  • strigger. Runs a program on events such as node down or job end.
  • --mail-type=END,FAIL. The original push notification, still useful for humans.

A practical combination for most sites: exporter + Prometheus for the cluster view, polling with accounting fallback for tools that track their own jobs, and a job-end webhook where something must react immediately.

6. Common objections, and honest answers

"This is more typing than sbatch job.sh." True, for a person. Nobody should hand-write JSON to submit their daily jobs. The JSON is written once, inside a script, portal or workflow tool, and then reused thousands of times. Compare it to writing a Puppet manifest versus typing commands on one server.

"Why not just have the portal SSH in and run sbatch?" Many do, and it works, but it has costs. The portal needs SSH keys for every user (or a shared account that hides who submitted). It must parse human-oriented text that changes between versions. Every request spawns a login session on a login node. Errors come back as free text. The API gives you structured errors, per-user tokens with expiry, and no shell sessions.

"Isn't opening an HTTP port to the scheduler a security risk?" It's a different risk, and a manageable one. slurmrestd runs as an unprivileged account (never root or SlurmUser). Every request must carry a valid token, and Slurm still enforces the user's normal permissions: you can't cancel someone else's job. Keep it on an internal network, put TLS and a reverse proxy in front, and set short token lifetimes. Compare that to the current alternative of SSH access for every portal and script.

"My job works with sbatch but fails through the API." Almost always the environment. sbatch copies your shell's PATH, modules and variables; the API copies nothing. Set environment explicitly, or start the script with source /etc/profile and module load ..., just as you would for a cron job.

"Does this make the scheduler slower?" Not by itself. slurmrestd makes the same RPCs the CLI makes. What adds load is aggressive polling, from either side. A portal polling the API once a second per job is just as bad as a script running squeue in a tight loop. Section 5 covers polling politely.

"Will my users have to learn this?" Most won't. They keep using sbatch, or they use a portal that uses the API underneath. The people who benefit directly are those writing tools: workflow developers, portal builders, and admins automating the cluster.

"The API version changes every release. Isn't that fragile?" The version in the URL is a feature: a client written for v0.0.42 keeps working while that version is supported, even after an upgrade adds v0.0.43. Slurm supports several versions at once and marks older ones deprecated before removing them. Plan to update clients every year or two, the same as any other API. That's still more stable than parsing CLI output, which has no contract at all.

7. Turning it on: admin checklist

On Rocky 8/9 with Slurm built with JWT support (libjwt), enabling the API takes about an hour in a test environment.

7.1 Enable JWT authentication

Create a signing key on the controller and make it available to slurmdbd:

dd if=/dev/random of=/var/spool/slurm/statesave/jwt_hs256.key bs=32 count=1
chown slurm:slurm /var/spool/slurm/statesave/jwt_hs256.key
chmod 0600 /var/spool/slurm/statesave/jwt_hs256.key

Add to both slurm.conf and slurmdbd.conf:

AuthAltTypes=auth/jwt
AuthAltParameters=jwt_key=/var/spool/slurm/statesave/jwt_hs256.key

Restart slurmdbd and slurmctld, then test with scontrol token. Keep the key away from any directory users can read: anyone holding it can mint tokens for any user.

7.2 Run slurmrestd as an unprivileged service

sudo useradd -M -r -s /usr/sbin/nologin -U slurmrestd
# /etc/sysconfig/slurmrestd
SLURMRESTD_LISTEN=:6820
# optional: SLURMRESTD_DEBUG=debug
sudo systemctl enable --now slurmrestd
curl -s -H "X-SLURM-USER-TOKEN: $(scontrol token | cut -d= -f2)" http://localhost:6820/slurm/v0.0.42/ping | jq .

The service account must not be root or SlurmUser. If you don't run slurmdbd, start slurmrestd with -s to skip the accounting endpoints. On 24.05 and later, set listen addresses only through SLURMRESTD_LISTEN, not in ExecStart. Run slurmrestd -d list to see which API versions your build supports.

7.3 Secure it before anyone else uses it

  • Listen on an internal interface only; firewall port 6820 to known clients.
  • Put a reverse proxy (nginx or Apache) in front for TLS, access logs and rate limiting.
  • Keep token lifetimes short for people. For services, issue tokens with scontrol token username=<svc> lifespan=... from root or SlurmUser, store them like passwords, and rotate them.
  • If users shouldn't mint their own tokens, set disable_token_creation in AuthAltParameters and issue tokens centrally, or use an authenticating proxy that adds X-SLURM-USER-NAME.
  • Log and alert: scrape the reverse proxy's metrics, and watch sdiag RPC counts (/slurm/V/diag) for clients that poll too aggressively.

7.4 Roll it out in stages

  1. Admins first. Replace a couple of sinfo/squeue-parsing cron scripts with API calls, and feed /diag and /nodes into Grafana.
  2. One tool second. Point a single workflow, dashboard or portal at the API, with its own service token.
  3. Users last, and optionally. Publish a short guide like section 4 for the few who write their own tooling. Everyone else keeps using sbatch.

8. The operational part: getting files to and from your jobs

slurmrestd moves no files, and neither does sbatch. Slurm schedules work. It has never copied your inputs anywhere. With the CLI you didn't notice, because you did the cp or rsync yourself from a login node onto a filesystem the compute nodes also mount, then submitted. The API removes the login-node shell, so the "cp step" needs a new home. Decide that first; everything else follows.

Every HPC run has the same five data steps:

 1. LOCATE        2. STAGE IN           3. RUN                 4. STAGE OUT            5. RETRIEVE
 test case   ──►  copy inputs to   ──►  job reads/writes  ──►  copy results to   ──►  client gets
 in a store       the run's workdir     (scratch / local)      a results store         results back
 (who?)           (who? when?)                                (who? when?)            (how?)

With sbatch, you did steps 2 and 5 by hand. With the API, each "who?" must be answered by software: the client, the job script, or a separate staging job.

8.1 Organize test cases so they can be found by name

A program can't browse directories the way you do, so give test cases a predictable layout and treat them as read-only:

/proj/testcases/                       ← read-only store (NetApp volume), versioned
  regress_cpu_core/v3/
    manifest.json                      ← list of files + sha256 checksums
    inputs/  design.tar.gz  stimulus/  run.tcl
/scratch/runs/                         ← one fresh directory per run, purged after N days
  2026-11-17_regress_cpu_core_v3_<jobid>/
/proj/results/                         ← kept results, one directory per run

Rules that save a lot of grief:

  • Never run in the test case directory. Copy or link inputs into a fresh run directory, so parallel runs can't overwrite each other.
  • Version test cases (v3), or pin them to a git commit (git LFS for large EDA vectors), so you can always say exactly what a run used.
  • Checksum inputs in a manifest. The job verifies them before spending hours of compute on a truncated file.
  • Name run directories after the job (%j), so the job record and the files can always be matched.

8.2 Five ways to do the "cp step"

Approach How inputs arrive How results return Best when
A. Shared filesystem on the client Client writes to an NFS/NetApp path that compute nodes also mount Client reads the same path The portal, CI runner or workflow host is inside the data center
B. Job stages from a central store Job script copies from /proj/testcases into its run dir Job script copies to /proj/results Test cases already live on the cluster; client just names which one
C. Object storage (S3) Client uploads with curl or the aws CLI; job downloads Job uploads; client downloads Client is outside the cluster (laptop, cloud CI, another site)
D. Staging jobs + dependencies A small stage-in job on a data-mover partition runs first A stage-out job runs after the compute job succeeds Big datasets; you want staging retried and accounted separately
E. Inline in the request Small text inputs embedded in the job script itself Small outputs written to stdout Config files and parameters of a few KB; never real data

Most sites end up with B as the default (the client sends a test case name, and the job does the copying), A for in-house tools, and C for anything outside.

8.3 Pattern B in practice: a job that stages itself

The client sends only which test case to run. The job script locates it, verifies it, stages it, runs it and saves the results. This script is what goes into the "script" field (or lives on the cluster and is called from a one-line script):

#!/bin/bash
set -euo pipefail
TC=${TESTCASE:?set TESTCASE}            # e.g. regress_cpu_core/v3, passed via "environment"
SRC=/proj/testcases/$TC
RUN=/scratch/runs/$(date +%F)_${TC//\//_}_${SLURM_JOB_ID}
DEST=/proj/results/${TC//\//_}/${SLURM_JOB_ID}

# 1. LOCATE: fail fast with a clear exit code if it isn't there
[[ -d $SRC ]] || { echo "testcase not found: $SRC" >&2; exit 3; }

# 2. STAGE IN: fresh run dir, then verify checksums
mkdir -p "$RUN" && cd "$RUN"
rsync -a "$SRC/inputs/" ./
jq -r '.files[] | "\(.sha256)  \(.path)"' "$SRC/manifest.json" | sha256sum -c --quiet \
  || { echo "checksum mismatch" >&2; exit 4; }

# 3. RUN (I/O-heavy tools: work on node-local disk instead, see 8.5)
./run.sh > run.log 2>&1

# 4. STAGE OUT: copy only what's worth keeping, record where it went
mkdir -p "$DEST"
rsync -a run.log reports/ "$DEST/"
echo "{\"job\": $SLURM_JOB_ID, \"testcase\": \"$TC\", \"results\": \"$DEST\"}" > "$DEST/result.json"

The matching API request just names the test case:

{ "job": {
    "name": "regress_cpu_core",
    "partition": "compute",
    "current_working_directory": "/scratch/runs",
    "standard_output": "/scratch/runs/%j.out",
    "environment": ["PATH=/usr/local/bin:/usr/bin:/bin", "TESTCASE=regress_cpu_core/v3"],
    "script": "#!/bin/bash\nexec /proj/tools/run_testcase.sh"
} }

Distinct exit codes (3 = not found, 4 = bad checksum) show up in accounting (/slurmdb/V/job/{id} → exit_code), so the client can tell "your test case is missing" from "the design failed" without reading any log.

8.4 Pattern C: object storage when the client is outside

When the client has no access to your filesystems, S3-compatible storage (MinIO, NetApp StorageGRID, or ONTAP S3) is the REST equivalent of a shared drive. Everything stays HTTP, which matches the API model:

# client: upload inputs, then hand the job a time-limited download URL
aws --endpoint-url https://s3.internal s3 cp design.tar.gz s3://hpc-in/run-0042/design.tar.gz
URL=$(aws --endpoint-url https://s3.internal s3 presign s3://hpc-in/run-0042/design.tar.gz --expires-in 86400)
# ...submit the job with "environment": [..., "INPUT_URL=$URL"]

# job script: stage in with plain curl (no credentials needed for a presigned URL)
curl -fsS -o design.tar.gz "$INPUT_URL" && tar xzf design.tar.gz
# ...run, then stage out with a service credential scoped to one bucket/prefix
aws --endpoint-url https://s3.internal s3 cp results.tar.gz s3://hpc-out/run-0042/

The client polls the job (section 5) and, when it shows COMPLETED, downloads from hpc-out. Presigned URLs expire, so the URL must outlive the job's queue time; issue them generously or refresh them at submit time.

8.5 Pattern D: staging as separate jobs, chained with dependencies

For large datasets, don't make a 64-node job sit idle while it copies 2 TB. Stage on a cheap data-mover partition first, and start the compute job only if staging succeeded. Dependencies work exactly as with sbatch --dependency:

IN=$(curl -s "${AUTH[@]}" -H 'Content-Type: application/json' --data-binary @stage_in.json  $SR/slurm/$V/job/submit | jq -r .job_id)

jq --arg d "afterok:$IN" '.job.dependency = $d' compute.json > c.json
RUN=$(curl -s "${AUTH[@]}" -H 'Content-Type: application/json' --data-binary @c.json $SR/slurm/$V/job/submit | jq -r .job_id)

jq --arg d "afterok:$RUN" '.job.dependency = $d' stage_out.json > o.json
curl -s "${AUTH[@]}" -H 'Content-Type: application/json' --data-binary @o.json $SR/slurm/$V/job/submit | jq -r .job_id

If staging fails, the compute job never starts. It shows DependencyNeverSatisfied, and the client sees exactly which step broke.

Inside a job, for node-local disk: many EDA and simulation tools perform badly on NFS. Copy inputs from shared storage to fast local disk ($TMPDIR or /tmp) at the start and copy results back at the end. Across a multi-node job, sbcast copies a file from the job's first node to the local disk of every allocated node:

sbcast /proj/testcases/regress_cpu_core/v3/inputs/design.tar.gz /tmp/design.tar.gz
srun tar xzf /tmp/design.tar.gz -C /tmp

8.6 Finding a run's files afterwards

The API tells you where a job ran and wrote, even though it doesn't hand you the files:

curl -s "${AUTH[@]}" $SR/slurm/$V/job/$JOBID | jq '.jobs[0] | {current_working_directory, standard_output, standard_error, nodes}'

After the job ages out, use the accounting record (/slurmdb/V/job/{id}), which also keeps the working directory. With the %j naming from 8.1 and the result.json the job writes, any tool can go from a job ID straight to its results without asking anyone.

8.7 If your researchers use Nextflow

Nextflow already does all of this for you. Each task runs in its own work directory under workDir (point it at scratch), inputs are staged in by symlink or copy (stageInMode), outputs are staged out (stageOutMode, publishDir), and scratch true runs tasks on node-local disk. Remote inputs on S3 or HTTP are fetched automatically. The admin's job is mostly to provide the right storage: a fast shared scratch for workDir, node-local disk, and a results store with a purge policy. The same five steps apply; Nextflow just answers the "who?" questions automatically.

8.8 Operational checklist

  • Decide the default staging pattern (B, C or D) and write it down for tool builders.
  • Read-only, versioned test case store with manifests and checksums.
  • Scratch with a published purge policy (for example 14 days), and a separate kept-results area with quotas.
  • Run directories and output files named with %j, so job IDs map to files.
  • Standard exit codes for staging failures, so clients can tell data problems from run failures.
  • For outside clients: an S3 endpoint, buckets for in/out, and service credentials scoped to a prefix.
  • A data-mover partition if you stage large data as separate jobs.
