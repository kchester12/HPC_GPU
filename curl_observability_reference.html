1. curl fundamentals for observability

Every modern observability component exposes plain HTTP: a health endpoint, a /metrics endpoint, and a JSON (sometimes protobuf) API. With curl and jq you can inspect, query and debug the whole stack without a UI. Examples assume a lab host; replace localhost and the ports with your own values.

Tools to have installed (Rocky 8/9):

sudo dnf install -y curl jq
# optional but handy
sudo dnf install -y python3   # for python3 -m json.tool when jq isn't there

The flags you will use constantly:

Flag What it does Why it matters here
-s Silent: no progress meter Clean output for piping to jq
-S Show errors even when silent Pair with -s as -sS
-f Fail (exit 22) on HTTP >= 400, print no body Health checks in scripts and cron
--fail-with-body Like -f but still prints the error body Debugging: APIs explain why in the body
-i / -I Include response headers / HEAD only See Content-Type, Content-Encoding, auth errors
-v Verbose: TLS handshake, request and response headers First stop for "it doesn't connect"
-w '%{http_code}\n' Print chosen variables after the transfer Status codes and timing without the body
-o /dev/null Discard the body Use with -w for pure status checks
-G + --data-urlencode Put URL-encoded params in the query string of a GET Essential for PromQL and LogQL (braces, quotes, spaces)
-H 'Header: value' Add a header Auth tokens, Content-Type, tenant IDs
-d / --data-binary @file Send a body (implies POST) Push APIs, OTLP, dashboard import
-X METHOD Force a method DELETE silences, PUT/POST admin calls
-u user:pass Basic auth Grafana admin, Elasticsearch, protected exporters
--max-time N / --connect-timeout N Bound the whole call / the connect phase Stops hung checks from piling up
--cacert, --cert, --key, -k TLS trust and mTLS client certs; -k skips verification Use -k only in a lab, never in a script you keep
--compressed Ask for gzip and decode it Large /metrics payloads
-N No output buffering Streaming endpoints (Loki tail via HTTP, SSE)

Status code only:

curl -s -o /dev/null -w '%{http_code}\n' http://localhost:9090/-/ready

Timing breakdown. This shows where latency comes from (DNS, TCP, TLS, server):

curl -s -o /dev/null -w 'dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total} size=%{size_download}\n' \
  http://localhost:9100/metrics

Safe URL encoding for query languages. Never hand-encode PromQL or LogQL. Let curl do it:

curl -sG http://localhost:9090/api/v1/query \
  --data-urlencode 'query=rate(node_cpu_seconds_total{mode!="idle"}[5m])' | jq .

Keep secrets out of shell history and ps:

# token in a file, read by curl
echo 'Authorization: Bearer glsa_xxx' > ~/.grafana.hdr && chmod 600 ~/.grafana.hdr
curl -sS -H @$HOME/.grafana.hdr http://grafana:3000/api/org

# or a ~/.netrc entry for basic auth
# machine grafana login admin password s3cret
curl -sS --netrc http://grafana:3000/api/org

jq essentials for these APIs:

jq .                          # pretty-print
jq -r '.status'               # raw string, no quotes
jq '.data.result | length'    # count items
jq -r '.data.result[] | "\(.metric.instance)\t\(.value[1])"'   # tab-separated report
jq 'keys'                     # discover the shape of an unfamiliar response

A study habit that works. For any new component, run these three things in order:

  1. Find its health endpoint (/-/healthy, /ready, /api/health, /healthz).
  2. Read its own /metrics. Every component in this guide instruments itself, and the metric names tell you what its internals do.
  3. Walk its API, starting from status/config endpoints and moving to the query endpoints.

2. Reading raw metrics: /metrics and exposition formats

A scrape is just an HTTP GET. If you can curl a target's /metrics from the Prometheus host, Prometheus can scrape it. If you can't, fix that first.

Scrape node_exporter by hand:

curl -s http://node01:9100/metrics | head -40

Anatomy of the text format. Every metric family has a HELP line, a TYPE line, then one sample per label set:

# HELP node_cpu_seconds_total Seconds the CPUs spent in each mode.
# TYPE node_cpu_seconds_total counter
node_cpu_seconds_total{cpu="0",mode="idle"} 81234.56
node_cpu_seconds_total{cpu="0",mode="system"} 1532.1
TYPE Meaning How you query it
counter Only goes up (resets on restart) Always wrap in rate() / increase()
gauge Goes up and down Use directly, or avg_over_time()
histogram _bucket{le=...}, _sum, _count series histogram_quantile(0.95, rate(x_bucket[5m]))
summary Pre-computed {quantile=...} plus _sum/_count Read quantiles directly; you can't aggregate them across instances
untyped / unknown No type declared Treat with care

Content negotiation. Prometheus asks for OpenMetrics first. You can see the difference yourself:

# classic Prometheus text format (version=0.0.4)
curl -s -H 'Accept: text/plain' http://node01:9100/metrics | head

# OpenMetrics: adds "# EOF", _created series, exemplars
curl -s -H 'Accept: application/openmetrics-text; version=1.0.0' http://node01:9100/metrics | tail -3

# what did the server actually return?
curl -sI -H 'Accept: application/openmetrics-text' http://node01:9100/metrics | grep -i content-type

Useful grep patterns while studying an exporter:

# list every metric family name and its type
curl -s http://node01:9100/metrics | awk '/^# TYPE/ {print $3, $4}' | sort | less

# count series per family (find cardinality hogs)
curl -s http://node01:9100/metrics | grep -v '^#' | sed 's/[{ ].*//' | sort | uniq -c | sort -rn | head -20

# total series this target produces
curl -s http://node01:9100/metrics | grep -vc '^#'

# one family, all label sets
curl -s http://node01:9100/metrics | grep '^node_filesystem_avail_bytes'

node_exporter specifics:

# which collectors ran, and did any fail?
curl -s http://node01:9100/metrics | grep -E '^node_scrape_collector_(success|duration_seconds)'

# textfile collector output (your own cron-written .prom files)
curl -s http://node01:9100/metrics | grep -E '^node_textfile_(scrape_error|mtime_seconds)'

# restrict a scrape to some collectors (node_exporter >= 1.0)
curl -s 'http://node01:9100/metrics?collect[]=cpu&collect[]=meminfo' | grep -c '^node_'

Gzip and size. Big exporters (kube-state-metrics, DCGM, Slurm exporters on large clusters) can return many megabytes:

curl -s --compressed -o /dev/null -w 'bytes=%{size_download} time=%{time_total}s\n' http://node01:9100/metrics

If scrape time gets close to the job's scrape_timeout, you'll see up == 0 with "context deadline exceeded" in the target's lastError.

Other exporters to study the same way:

Exporter Default port Worth looking at
node_exporter 9100 node_*, collector success
blackbox_exporter 9115 /probe?target=...&module=http_2xx (see below)
process-exporter 9256 per-process-group CPU/mem
mysqld_exporter (MariaDB) 9104 mysql_up, mysql_global_status_*
NVIDIA DCGM exporter 9400 DCGM_FI_DEV_GPU_UTIL, DCGM_FI_DEV_FB_USED
Grafana / Prometheus / Loki / Alertmanager self-metrics their own ports /metrics on each

blackbox_exporter, the "curl as a service":

# probe an HTTP endpoint with the http_2xx module, see what Prometheus would record
curl -s 'http://localhost:9115/probe?target=https://grafana.example.com&module=http_2xx' \
  | grep -E '^probe_(success|http_status_code|duration_seconds|ssl_earliest_cert_expiry)'

# add debug=true to see the probe's full log
curl -s 'http://localhost:9115/probe?target=node01:22&module=tcp_connect&debug=true'

3. Prometheus server HTTP API

The Prometheus API lives under /api/v1/. Every response is JSON with status (success or error), data, and on failure errorType and error. Set P=http://localhost:9090 once and reuse it.

P=http://localhost:9090

3.1 Health and lifecycle

curl -fsS $P/-/healthy      # process is up               -> "Prometheus Server is Healthy."
curl -fsS $P/-/ready        # TSDB loaded, serving queries -> "Prometheus Server is Ready." (503 while replaying WAL)
curl -fsS -X POST $P/-/reload   # re-read prometheus.yml + rules (needs --web.enable-lifecycle)
curl -fsS -X POST $P/-/quit     # graceful shutdown (needs --web.enable-lifecycle)

If you don't want to enable lifecycle, kill -HUP $(pidof prometheus) reloads too.

3.2 Build, config, flags, runtime

curl -s $P/api/v1/status/buildinfo | jq .data              # version, revision, go version
curl -s $P/api/v1/status/runtimeinfo | jq .data            # reloadConfigSuccess, lastConfigTime, storageRetention, goroutines
curl -s $P/api/v1/status/flags | jq .data                  # every CLI flag in effect
curl -s $P/api/v1/status/config | jq -r .data.yaml         # the loaded config (secrets redacted)
curl -s $P/api/v1/status/walreplay | jq .data              # WAL replay progress after a restart

runtimeinfo.reloadConfigSuccess == false is the fastest way to learn that your last edit to prometheus.yml didn't apply.

3.3 Targets: is everything being scraped?

# all active targets: instance, job, health, last error, scrape duration
curl -s $P/api/v1/targets?state=active | jq -r '.data.activeTargets[] |
  [.labels.job, .labels.instance, .health, (.lastScrapeDuration|tostring), .lastError] | @tsv' | column -t -s $'\t'

# only the broken ones
curl -s $P/api/v1/targets | jq -r '.data.activeTargets[] | select(.health != "up") | "\(.scrapeUrl)  \(.lastError)"'

# targets dropped by relabeling (why isn't my node showing up?)
curl -s $P/api/v1/targets?state=dropped | jq '.data.droppedTargets | length'

# what metadata does a target expose?
curl -sG $P/api/v1/targets/metadata --data-urlencode 'match_target={job="node"}' --data-urlencode 'metric=node_load1' | jq .data

3.4 Instant queries

/api/v1/query evaluates PromQL at one point in time (now, unless you pass time).

# who is up?
curl -sG $P/api/v1/query --data-urlencode 'query=up' |
  jq -r '.data.result[] | "\(.metric.job)\t\(.metric.instance)\t\(.value[1])"'

# CPU busy % per node over the last 5 minutes
curl -sG $P/api/v1/query --data-urlencode \
  'query=100 * (1 - avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])))' |
  jq -r '.data.result[] | "\(.metric.instance)\t\(.value[1] | tonumber | floor)%"' | sort -k2 -n -r

# filesystems with less than 10% free
curl -sG $P/api/v1/query --data-urlencode \
  'query=node_filesystem_avail_bytes{fstype!~"tmpfs|overlay"} / node_filesystem_size_bytes < 0.10' | jq '.data.result'

# evaluate at a past moment (RFC3339 or unix seconds)
curl -sG $P/api/v1/query --data-urlencode 'query=up' --data-urlencode 'time=2026-11-17T08:00:00Z' | jq '.data.result | length'

# POST works too; use it for very long queries
curl -s $P/api/v1/query --data-urlencode 'query=sum(up)' | jq .

Result types you'll see in .data.resultType: vector (instant), matrix (range), scalar, string. Values are always [unix_ts, "string_number"], so convert with tonumber in jq.

3.5 Range queries (what Grafana graphs do)

START=$(date -d '-1 hour' +%s); END=$(date +%s)
curl -sG $P/api/v1/query_range \
  --data-urlencode 'query=node_load1{instance="node01:9100"}' \
  --data-urlencode "start=$START" --data-urlencode "end=$END" --data-urlencode 'step=60' |
  jq -r '.data.result[0].values[] | "\(.[0] | todate)\t\(.[1])"'

The number of points is (end - start) / step. Prometheus refuses more than 11,000 points per series, so widen step for long ranges.

3.6 Discovery: series, labels, metadata

# all label names
curl -s $P/api/v1/labels | jq -r '.data[]'

# all values of one label (e.g. every instance, every job)
curl -s $P/api/v1/label/instance/values | jq -r '.data[]'

# all metric names (it's just the values of __name__)
curl -s $P/api/v1/label/__name__/values | jq -r '.data[]' | grep ^node_ | wc -l

# series matching a selector, limited to a time window
curl -sG $P/api/v1/series --data-urlencode 'match[]=node_network_receive_bytes_total{instance="node01:9100"}' \
  --data-urlencode "start=$(date -d '-15 min' +%s)" | jq -r '.data[].device'

# HELP / TYPE / unit for metrics (from scrapes)
curl -sG $P/api/v1/metadata --data-urlencode 'metric=node_memory_MemAvailable_bytes' | jq .data

# exemplars (trace IDs attached to histogram samples, if enabled)
curl -sG $P/api/v1/query_exemplars --data-urlencode 'query=http_request_duration_seconds_bucket' \
  --data-urlencode "start=$START" --data-urlencode "end=$END" | jq .data

3.7 Rules and alerts

# every rule group, its health and last evaluation error
curl -s $P/api/v1/rules | jq -r '.data.groups[] | .name as $g | .rules[] | "\($g)\t\(.type)\t\(.name)\t\(.health)\t\(.lastError // "")"'

# only alerting rules, with current state
curl -s "$P/api/v1/rules?type=alert" | jq -r '.data.groups[].rules[] | "\(.state)\t\(.name)"'

# currently pending/firing alerts as Prometheus sees them
curl -s $P/api/v1/alerts | jq -r '.data.alerts[] | "\(.state)\t\(.labels.alertname)\t\(.labels.instance // "-")\t\(.activeAt)"'

# which Alertmanagers is Prometheus sending to?
curl -s $P/api/v1/alertmanagers | jq '.data.activeAlertmanagers'

Check rule files offline before you reload: promtool check rules /etc/prometheus/rules/*.yml and promtool check config /etc/prometheus/prometheus.yml.

3.8 Formatting and parsing queries

# pretty-print a PromQL expression (Prometheus >= 2.38)
curl -sG $P/api/v1/format_query --data-urlencode 'query=sum(rate(x[5m]))by(job)' | jq -r .data

# parse to an AST (newer versions, may need --enable-feature=promql-experimental-functions)
curl -sG $P/api/v1/parse_query --data-urlencode 'query=up == 0' | jq .data

3.9 TSDB status: cardinality and storage

curl -s $P/api/v1/status/tsdb | jq '.data.headStats'                         # numSeries, chunks, minTime/maxTime
curl -s $P/api/v1/status/tsdb | jq -r '.data.seriesCountByMetricName[] | "\(.value)\t\(.name)"'   # top metrics by series
curl -s $P/api/v1/status/tsdb | jq -r '.data.labelValueCountByLabelName[] | "\(.value)\t\(.name)"'  # high-cardinality labels

This is the first place to look when Prometheus memory grows. A label like jobid, user or pid on a node-level metric shows up here immediately.

3.10 Admin APIs (need --web.enable-admin-api)

# consistent snapshot of the TSDB to <data-dir>/snapshots/
curl -s -X POST $P/api/v1/admin/tsdb/snapshot | jq .

# delete series (marks tombstones), then compact them away
curl -s -X POST -g "$P/api/v1/admin/tsdb/delete_series?match[]={instance=\"oldnode:9100\"}"
curl -s -X POST $P/api/v1/admin/tsdb/clean_tombstones

The admin API can destroy data. Keep it off by default, or bind Prometheus to localhost behind a reverse proxy.

3.11 Ingest APIs (when enabled)

Endpoint Flag Use
POST /api/v1/write --web.enable-remote-write-receiver Accept remote-write from other Prometheus / agents (snappy protobuf, not curl-friendly)
POST /api/v1/otlp/v1/metrics --web.enable-otlp-receiver (3.x) Accept OTLP metrics directly (see section 8)
/federate?match[]=... none Pull current values in text format from another Prometheus 
curl -sG $P/federate --data-urlencode 'match[]={job="node"}' | head

3.12 Errors you'll meet

HTTP errorType Typical cause
400 bad_data PromQL syntax error, usually unencoded braces or quotes (use -G --data-urlencode)
422 execution Query valid but failed: too many samples, mixed types
503 timeout / unavailable Query exceeded --query.timeout, or TSDB not ready
404 n/a Lifecycle or admin endpoint called without its flag

4. Pushgateway and Prometheus-compatible backends

4.1 Pushgateway (port 9091)

Pushgateway is for short-lived batch jobs that end before Prometheus can scrape them, for example a nightly backup, a Puppet run, or a Slurm epilog. The job pushes once, and Prometheus scrapes the gateway.

PG=http://localhost:9091

# push one metric: grouping key is /job/<name>[/<label>/<value>...]
echo 'backup_last_success_timestamp_seconds 1763390000' | \
  curl -sS --data-binary @- $PG/metrics/job/nightly_backup/host/nfs01

# push several, with HELP/TYPE (body must end with a newline)
cat <<'EOF' | curl -sS --data-binary @- $PG/metrics/job/puppet_run/instance/node01
# TYPE puppet_run_duration_seconds gauge
puppet_run_duration_seconds 42.7
# TYPE puppet_resources_failed gauge
puppet_resources_failed 0
EOF

# POST replaces only same-named metrics in the group; PUT replaces the whole group
curl -sS -X PUT --data-binary @metrics.txt $PG/metrics/job/puppet_run/instance/node01

# delete a group (do this when a host is decommissioned, or its stale value lives forever)
curl -sS -X DELETE $PG/metrics/job/puppet_run/instance/node01

# inspect what's stored
curl -s $PG/api/v1/metrics | jq -r '.data[] | .labels | "\(.job) \(.instance // "")"'
curl -s $PG/api/v1/status | jq .data
curl -fsS $PG/-/healthy && curl -fsS $PG/-/ready

Pushgateway adds push_time_seconds and push_failure_time_seconds per group. Alert on time() - push_time_seconds > 86400 to catch jobs that silently stopped. In the scrape job, set honor_labels: true.

4.2 Long-term storage backends speak the same query API

Thanos, Grafana Mimir, Cortex and VictoriaMetrics all implement the Prometheus /api/v1/query*, /api/v1/series and /api/v1/labels endpoints. Everything in section 3.4 to 3.6 works against them after you change the base URL and add the right headers.

Backend Query base URL (typical) Extra headers / notes Health
Thanos Query http://thanos-query:10902 dedup=true, partial_response=true params /-/healthy, /-/ready
Grafana Mimir http://mimir:8080/prometheus X-Scope-OrgID: <tenant> (required when multi-tenant) /ready, /config, /services
Cortex http://cortex/prometheus X-Scope-OrgID /ready
VictoriaMetrics single http://vm:8428 none /health
VictoriaMetrics cluster http://vmselect:8481/select/<accountID>/prometheus tenant in path /health 
# Mimir: same PromQL, plus tenant header
curl -sG -H 'X-Scope-OrgID: hpc' http://mimir:8080/prometheus/api/v1/query \
  --data-urlencode 'query=count(up)' | jq .

# Thanos: deduplicate HA replicas, see which stores answered
curl -sG http://thanos-query:10902/api/v1/query --data-urlencode 'query=up' \
  --data-urlencode 'dedup=true' | jq '.data.result | length'
curl -s http://thanos-query:10902/api/v1/stores | jq .

# VictoriaMetrics extras: export raw samples, check cardinality
curl -sG http://vm:8428/api/v1/export --data-urlencode 'match[]=node_load1' | head -2
curl -s http://vm:8428/api/v1/status/tsdb | jq '.data.seriesCountByMetricName[:5]'

# VictoriaMetrics accepts Prometheus text format via HTTP import
echo 'test_metric{src="curl"} 1' | curl -sS --data-binary @- http://vm:8428/api/v1/import/prometheus

5. Alertmanager API v2 (port 9093)

Alertmanager receives alerts from Prometheus, groups and deduplicates them, applies silences and inhibitions, and routes them to receivers. Its API is /api/v2/ (v1 was removed in 0.27). amtool wraps the same API, but curl shows you exactly what goes over the wire.

AM=http://localhost:9093
curl -fsS $AM/-/healthy; curl -fsS $AM/-/ready

5.1 Status and cluster

curl -s $AM/api/v2/status | jq '{version: .versionInfo.version, uptime, cluster: .cluster.status, peers: [.cluster.peers[].address]}'
curl -s $AM/api/v2/status | jq -r .config.original     # the loaded alertmanager.yml
curl -s $AM/api/v2/receivers | jq -r '.[].name'

In an HA pair, cluster.status should be ready and every peer should be listed. If it isn't, notifications get duplicated.

5.2 Reading alerts

# everything Alertmanager currently holds
curl -s $AM/api/v2/alerts | jq -r '.[] | "\(.status.state)\t\(.labels.alertname)\t\(.labels.instance // "-")\t\(.startsAt)"'

# filter server-side with matchers; exclude silenced and inhibited
curl -sG $AM/api/v2/alerts \
  --data-urlencode 'filter=severity="critical"' \
  --data-urlencode 'silenced=false' --data-urlencode 'inhibited=false' | jq length

# grouped as they'd be notified
curl -s $AM/api/v2/alerts/groups | jq -r '.[] | "\(.receiver.name)\t\(.labels)\t\(.alerts | length) alerts"'

5.3 Firing a test alert (test your routing without breaking anything)

NOW=$(date -u +%Y-%m-%dT%H:%M:%SZ)
END=$(date -u -d '+5 min' +%Y-%m-%dT%H:%M:%SZ)
curl -sS -X POST $AM/api/v2/alerts -H 'Content-Type: application/json' -d "[{
  \"labels\": {\"alertname\": \"CurlTestAlert\", \"severity\": \"warning\", \"instance\": \"node01\", \"team\": \"hpc\"},
  \"annotations\": {\"summary\": \"Test alert sent with curl\", \"description\": \"Safe to ignore\"},
  \"startsAt\": \"$NOW\", \"endsAt\": \"$END\",
  \"generatorURL\": \"http://localhost/curl-test\"
}]" -w '%{http_code}\n'

Alertmanager returns 200 with an empty body. Then check that it landed in the right group and receiver (5.2). To resolve it early, POST the same labels with endsAt set to now.

This is also how non-Prometheus tools can raise alerts. A Slurm health-check script or your BMC recovery script can POST straight to Alertmanager and use the same routing and silencing.

5.4 Silences

# create a 2-hour maintenance silence for one node
curl -sS -X POST $AM/api/v2/silences -H 'Content-Type: application/json' -d "{
  \"matchers\": [{\"name\": \"instance\", \"value\": \"node01.*\", \"isRegex\": true, \"isEqual\": true}],
  \"startsAt\": \"$(date -u +%Y-%m-%dT%H:%M:%SZ)\",
  \"endsAt\": \"$(date -u -d '+2 hours' +%Y-%m-%dT%H:%M:%SZ)\",
  \"createdBy\": \"$USER\",
  \"comment\": \"Firmware update via iLO\"
}" | jq -r .silenceID

# list active silences
curl -s $AM/api/v2/silences | jq -r '.[] | select(.status.state=="active") | "\(.id)\t\(.endsAt)\t\(.createdBy)\t\(.comment)"'

# expire (delete) a silence
curl -sS -X DELETE $AM/api/v2/silence/<silenceID>

To extend a silence, POST it again with its id field included and a new endsAt.

5.5 Webhook receivers: see what Alertmanager sends

To study the notification payload, point a webhook_configs receiver at a throwaway listener and fire a test alert:

# listener (prints the raw POST body)
python3 -c 'import http.server as h
class H(h.BaseHTTPRequestHandler):
  def do_POST(s):
    print(s.rfile.read(int(s.headers["Content-Length"])).decode()); s.send_response(200); s.end_headers()
h.HTTPServer(("0.0.0.0",5001),H).serve_forever()'

The body is the webhook v4 format: receiver, status, groupLabels, commonLabels, externalURL and an alerts[] array.

6. Grafana HTTP API (port 3000)

Anything you click in Grafana is a call to /api/.... Learning the API lets you back up dashboards, provision data sources, run queries through Grafana, and drop annotations from scripts. Open the browser dev tools (Network tab) on any Grafana page to see the exact call a button makes, then replay it with curl.

G=http://localhost:3000
curl -s $G/api/health | jq .      # {"database":"ok","version":"..."}; no auth needed

6.1 Authentication

Method How Use for
Basic auth -u admin:password First-time setup, labs
Service account token -H 'Authorization: Bearer glsa_...' Scripts and automation (API keys are deprecated)
Org context -H 'X-Grafana-Org-Id: 2' Calls against a non-default org 
# create a service account + token (as admin)
SA=$(curl -s -u admin:admin -H 'Content-Type: application/json' \
  -d '{"name":"automation","role":"Editor"}' $G/api/serviceaccounts | jq -r .id)
curl -s -u admin:admin -H 'Content-Type: application/json' \
  -d '{"name":"cli"}' $G/api/serviceaccounts/$SA/tokens | jq -r .key > ~/.grafana_token
chmod 600 ~/.grafana_token

AUTH="Authorization: Bearer $(cat ~/.grafana_token)"
curl -s -H "$AUTH" $G/api/user | jq '{login, orgId}'

6.2 Instance and org info

curl -s -H "$AUTH" $G/api/frontend/settings | jq '.buildInfo'
curl -s -u admin:admin $G/api/admin/stats | jq '{dashboards, datasources, users, alerts}'
curl -s -u admin:admin $G/api/orgs | jq -r '.[] | "\(.id)\t\(.name)"'

7. Loki: logs over HTTP (port 3100)

Loki indexes only labels and stores log lines as compressed chunks. Its API has a write side (/loki/api/v1/push) and a read side that mirrors Prometheus (query, query_range, labels, series). Multi-tenant installs need X-Scope-OrgID on every call.

L=http://localhost:3100
curl -fsS $L/ready                     # "ready" (may say "Ingester not ready: waiting for 15s after being ready" at startup)
curl -s $L/loki/api/v1/status/buildinfo | jq .
curl -s $L/services                    # every internal module and its state
curl -s $L/config | head -50           # effective config (YAML)

7.1 Push a log line

Timestamps are nanosecond epoch strings.

TS=$(date +%s%N)
curl -sS -H 'Content-Type: application/json' $L/loki/api/v1/push -d "{
  \"streams\": [{
    \"stream\": {\"job\": \"curl-test\", \"host\": \"$(hostname -s)\", \"level\": \"info\"},
    \"values\": [[\"$TS\", \"hello from curl, user=$USER\"]]
  }]
}" -w '%{http_code}\n'      # 204 = accepted

Common rejections: 400 entry too far behind (timestamp older than the stream's newest), 429 (rate limits), and 400 ... labels (too many labels, or high-cardinality labels like a job ID). Put high-cardinality values in the log line or in structured metadata, not in labels.

7.2 Discover labels and streams

curl -s $L/loki/api/v1/labels | jq -r '.data[]'
curl -s $L/loki/api/v1/label/job/values | jq -r '.data[]'
curl -sG $L/loki/api/v1/series --data-urlencode 'match[]={job="varlogs"}' | jq '.data | length'

# size of what a selector would scan (Loki >= 2.8)
curl -sG $L/loki/api/v1/index/stats --data-urlencode 'query={job="varlogs"}' \
  --data-urlencode "start=$(date -d '-1 day' +%s)000000000" | jq .

7.3 Query logs (LogQL)

# last hour of slurmctld errors, newest first
curl -sG $L/loki/api/v1/query_range \
  --data-urlencode 'query={job="slurm", host="head01"} |= "error"' \
  --data-urlencode "start=$(date -d '-1 hour' +%s)" \
  --data-urlencode 'limit=50' --data-urlencode 'direction=backward' |
  jq -r '.data.result[] | .values[] | "\(.[0] | tonumber / 1e9 | todate)  \(.[1])"'

# parse and filter: sshd failed logins by source IP
curl -sG $L/loki/api/v1/query_range \
  --data-urlencode 'query={job="varlogs"} |= "Failed password" | regexp "from (?P<ip>\\S+)"' \
  --data-urlencode "start=$(date -d '-6 hours' +%s)" | jq -r '.data.result[].stream.ip' | sort | uniq -c | sort -rn

# metric query: log lines per host per 5m (returns a matrix like Prometheus)
curl -sG $L/loki/api/v1/query_range \
  --data-urlencode 'query=sum by (host) (count_over_time({job="varlogs"} |= "oom-kill" [5m]))' \
  --data-urlencode "start=$(date -d '-1 day' +%s)" --data-urlencode 'step=300' | jq '.data.result[] | {host: .metric.host, points: (.values|length)}'

# instant metric query
curl -sG $L/loki/api/v1/query --data-urlencode 'query=sum(count_over_time({job="varlogs"}[1h]))' | jq '.data.result'

start/end accept seconds, nanoseconds or RFC3339. The default range is the last hour, and limit defaults to 100.

7.4 Live tail

8. OpenTelemetry, Tempo and Jaeger: traces (and OTLP for everything)

OTLP is the vendor-neutral wire protocol for traces, metrics and logs. It runs over gRPC on port 4317 and over HTTP on port 4318. The HTTP form accepts JSON, so you can hand-craft telemetry with curl and watch it flow through the Collector into Tempo, Prometheus and Loki.

8.1 OpenTelemetry Collector endpoints

Port Extension / receiver What curl gets you
4318 otlp receiver, HTTP POST /v1/traces, /v1/metrics, /v1/logs
4317 otlp receiver, gRPC Not curl; use grpcurl
13133 health_check extension GET / → {"status":"Server available",...}
55679 zpages extension /debug/tracez, /debug/pipelinez, /debug/servicez (HTML)
8888 Collector self-telemetry /metrics: otelcol_receiver_accepted_*, otelcol_exporter_send_failed_*
1777 pprof extension /debug/pprof/ profiles 
OC=http://localhost
curl -fsS $OC:13133/ | jq .
curl -s $OC:8888/metrics | grep -E '^otelcol_(receiver_accepted|receiver_refused|exporter_sent|exporter_send_failed)_spans'
curl -s $OC:55679/debug/pipelinez | sed 's/<[^>]*>//g' | grep -v '^\s*$' | head -40

If receiver_accepted grows but exporter_sent doesn't, the backend is the problem. If receiver_refused grows, look at the memory limiter or your payload.

8.2 Send a trace by hand

Trace IDs are 32 hex characters, span IDs are 16, and times are nanoseconds.

TRACE=$(openssl rand -hex 16); SPAN=$(openssl rand -hex 8); CHILD=$(openssl rand -hex 8)
T0=$(date +%s%N); T1=$((T0 + 250000000)); T2=$((T0 + 900000000))

curl -sS $OC:4318/v1/traces -H 'Content-Type: application/json' -d "{
 \"resourceSpans\": [{
  \"resource\": {\"attributes\": [
    {\"key\": \"service.name\", \"value\": {\"stringValue\": \"curl-demo\"}},
    {\"key\": \"host.name\", \"value\": {\"stringValue\": \"$(hostname -s)\"}}]},
  \"scopeSpans\": [{\"scope\": {\"name\": \"manual\"}, \"spans\": [
    {\"traceId\": \"$TRACE\", \"spanId\": \"$SPAN\", \"name\": \"submit-job\", \"kind\": 2,
     \"startTimeUnixNano\": \"$T0\", \"endTimeUnixNano\": \"$T2\",
     \"attributes\": [{\"key\": \"slurm.partition\", \"value\": {\"stringValue\": \"gpu\"}}],
     \"status\": {\"code\": 1}},
    {\"traceId\": \"$TRACE\", \"spanId\": \"$CHILD\", \"parentSpanId\": \"$SPAN\", \"name\": \"stage-data\", \"kind\": 1,
     \"startTimeUnixNano\": \"$T0\", \"endTimeUnixNano\": \"$T1\"}
  ]}]
 }]
}" -w '\n%{http_code}\n'
echo "trace id: $TRACE"

A 200 with {"partialSuccess":{}} (or an empty body) means accepted. Span kind: 1 internal, 2 server, 3 client, 4 producer, 5 consumer. Status code: 0 unset, 1 OK, 2 error.

8.3 Send metrics and logs over OTLP

# a gauge
curl -sS $OC:4318/v1/metrics -H 'Content-Type: application/json' -d "{
 \"resourceMetrics\": [{\"resource\": {\"attributes\": [{\"key\":\"service.name\",\"value\":{\"stringValue\":\"curl-demo\"}}]},
  \"scopeMetrics\": [{\"metrics\": [{\"name\": \"demo.queue.depth\", \"unit\": \"1\",
    \"gauge\": {\"dataPoints\": [{\"asInt\": \"42\", \"timeUnixNano\": \"$(date +%s%N)\",
      \"attributes\": [{\"key\":\"partition\",\"value\":{\"stringValue\":\"gpu\"}}]}]}}]}]}]}"

# a log record correlated with the trace above
curl -sS $OC:4318/v1/logs -H 'Content-Type: application/json' -d "{
 \"resourceLogs\": [{\"resource\": {\"attributes\": [{\"key\":\"service.name\",\"value\":{\"stringValue\":\"curl-demo\"}}]},
  \"scopeLogs\": [{\"logRecords\": [{\"timeUnixNano\": \"$(date +%s%N)\", \"severityNumber\": 17, \"severityText\": \"ERROR\",
    \"body\": {\"stringValue\": \"stage-data failed: NFS timeout\"},
    \"traceId\": \"$TRACE\", \"spanId\": \"$CHILD\"}]}]}]}"

With a debug exporter (verbosity: detailed) in the pipeline, journalctl -u otelcol -f shows each item arriving. That is the quickest way to learn the data model.

Prometheus 3.x can take OTLP metrics directly at POST /api/v1/otlp/v1/metrics (start it with --web.enable-otlp-receiver). Loki 3.x accepts OTLP logs at POST /otlp/v1/logs.

8.4 Tempo (HTTP port 3200)

T=http://localhost:3200
curl -fsS $T/ready; curl -s $T/status/buildinfo | jq .

# fetch the trace you just sent (v2 API returns OTLP JSON)
curl -s $T/api/v2/traces/$TRACE | jq '.trace.resourceSpans[].scopeSpans[].spans[] | {name, spanId, parentSpanId}'

# TraceQL search: slow or failed spans from one service in the last hour
curl -sG $T/api/search \
  --data-urlencode 'q={ resource.service.name = "curl-demo" && (duration > 500ms || status = error) }' \
  --data-urlencode "start=$(date -d '-1 hour' +%s)" --data-urlencode "end=$(date +%s)" --data-urlencode 'limit=20' |
  jq -r '.traces[] | "\(.traceID)\t\(.rootServiceName)\t\(.rootTraceName)\t\(.durationMs)ms"'

# discover attributes and values
curl -s $T/api/v2/search/tags | jq .
curl -s $T/api/v2/search/tag/resource.service.name/values | jq -r '.tagValues[].value'

# TraceQL metrics (Tempo >= 2.4): span rate by service
curl -sG $T/api/metrics/query_range --data-urlencode 'q={} | rate() by (resource.service.name)' \
  --data-urlencode "start=$(date -d '-1 hour' +%s)" --data-urlencode 'step=60s' | jq '.series | length'

Traces can take a few seconds to become searchable. Fetch by ID works first because it reads the ingester directly.

8.5 Jaeger (query port 16686)

Jaeger v2 is built on the OpenTelemetry Collector, so it also accepts OTLP on 4317/4318.

J=http://localhost:16686
curl -s $J/api/services | jq -r '.data[]'
curl -s "$J/api/services/curl-demo/operations" | jq -r '.data[]'
curl -sG $J/api/traces --data-urlencode 'service=curl-demo' --data-urlencode 'lookback=1h' --data-urlencode 'limit=10' \
  | jq -r '.data[] | "\(.traceID)\t\(.spans | length) spans"'
curl -s $J/api/traces/$TRACE | jq '.data[0].spans[] | {operationName, duration}'

# newer stable API (Jaeger v2): /api/v3/...
curl -s $J/api/v3/services | jq .

The /api/... paths are the UI's internal API and work well for study, but the documented stable API is /api/v3 (and gRPC).

curl -s "${A[@]}" "$ES/_cat/indices?v&s=store.size:desc&h=health,index,docs.count,store.size" | head

curl -s "${A[@]}" "$ES/_cluster/allocation/explain?pretty"    # WHY a shard is unassigned

9.2 The healthz / livez / readyz convention

Kubernetes popularized three probes, and many cloud-native tools now copy them:

Probe Question it answers Failure means
/livez (older: /healthz) Is the process alive? Restart it
/readyz Can it serve traffic right now? Take it out of the load balancer, don't restart it
/startupz or startup probe Has it finished initializing? Wait longer 
# Kubernetes API server (verbose shows each sub-check)

10.2 One-shot stack health check

Save this as obs-check.sh. It exits non-zero if anything fails, so you can run it from cron, a Slurm health check, or Nagios-style tooling.

#!/usr/bin/env bash
# obs-check.sh: probe every observability endpoint, print a status table
set -u
HOST=${1:-localhost}
TIMEOUT=5
fail=0

check() {   # name url [expected-substring]
  local name=$1 url=$2 want=${3:-} body code t
  body=$(curl -sS --max-time $TIMEOUT -w '\n%{http_code} %{time_total}' "$url" 2>&1)
  read -r code t <<<"$(tail -n1 <<<"$body")"
  body=$(sed '$d' <<<"$body")
  if [[ $code =~ ^2 ]] && { [[ -z $want ]] || grep -q "$want" <<<"$body"; }; then
    printf '%-16s OK    %3s %6.3fs  %s\n' "$name" "$code" "$t" "$url"
  else
    printf '%-16s FAIL  %3s %6ss  %s\n' "$name" "${code:-000}" "${t:--}" "$url"; fail=1
  fi
}

check prometheus    http://$HOST:9090/-/ready
check prom-config   http://$HOST:9090/api/v1/status/runtimeinfo '"reloadConfigSuccess":true'
check alertmanager  http://$HOST:9093/-/ready
check grafana       http://$HOST:3000/api/health '"database": *"ok"'
check node_exporter http://$HOST:9100/metrics 'node_exporter_build_info'
check loki          http://$HOST:3100/ready 'ready'
check otelcol       http://$HOST:13133/ 'Server available'

# scrape-target summary straight from Prometheus
down=$(curl -s --max-time $TIMEOUT http://$HOST:9090/api/v1/targets |
       jq -r '[.data.activeTargets[] | select(.health!="up")] | length' 2>/dev/null)
if [[ ${down:-x} == 0 ]]; then echo "targets          OK    all scrape targets up"
else echo "targets          FAIL  ${down:-?} target(s) down"; fail=1
  curl -s http://$HOST:9090/api/v1/targets | jq -r '.data.activeTargets[] | select(.health!="up") | "   - \(.scrapeUrl): \(.lastError)"'
fi
exit $fail

To test end-to-end, chain the write and read sides: push a line to Loki (7.1), push a metric to Pushgateway (4.1), send a span to the Collector (8.2), then read all three back. If each one shows up, every pipe in between works.

Symptom curl that pinpoints it Usual fix
Connection refused curl -v http://host:port/ + ss -ltnp | grep port on the host Service down, or bound to 127.0.0.1 only (--web.listen-address, http_listen_address)
Hangs then times out curl -v --connect-timeout 3 ... firewalld (firewall-cmd --add-port=9100/tcp --permanent), routing, SELinux port label
Target up == 0, "context deadline exceeded" curl -s -o /dev/null -w '%{time_total}' http://node:9100/metrics from the Prometheus host Exporter too slow or too big; raise scrape_timeout, disable heavy collectors
Target up == 0, "server returned HTTP status 401/403" curl -i the scrape URL Add basic_auth / authorization to the scrape config
bad_data: parse error Re-run with -G --data-urlencode 'query=...' Braces, quotes or + weren't URL-encoded
Config edit has no effect curl -s $P/api/v1/status/runtimeinfo | jq .data.reloadConfigSuccess promtool check config, then reload; read journalctl -u prometheus
Alert fires in Prometheus but no notification curl $P/api/v1/alertmanagers then curl $AM/api/v2/alerts then curl $AM/api/v2/silences Wrong Alertmanager URL, alert silenced or inhibited, route doesn't match
Grafana panel says "No data" Replay the panel query via /api/ds/query, then directly against the backend Wrong data source UID, time range, or label typo; Grafana can't reach backend (proxy access)
Loki push 400 / 429 curl -i the push and read the body Out-of-order timestamps, too many labels, ingestion rate limits
Prometheus memory climbing curl $P/api/v1/status/tsdb | jq .data.seriesCountByMetricName Drop high-cardinality labels with metric_relabel_configs
TLS errors curl -v --cacert ca.pem https://...; openssl s_client -connect host:port -showcerts Wrong CA, hostname not in SAN, expired cert (watch probe_ssl_earliest_cert_expiry)

10.4 A study path

  1. Scrape node_exporter by hand and learn the four metric types from real output (section 2).
  2. Reproduce your three most-used Grafana panels as /api/v1/query_range calls (sections 3.5, 6.4).
  3. Walk targets, rules and status/tsdb until you can explain every target and the top 10 metrics by series count (3.3, 3.7, 3.9).
  4. Fire a test alert, silence it, and capture the webhook payload (section 5).
  5. Push and query a log line, then turn it into a metric query (section 7).
  6. Send a hand-built trace with a correlated log, and find both (section 8).
  7. Wrap it all in obs-check.sh and run it on a schedule.
