Tracing an MPI or Training Job End to End

Start from the Slurm job ID and map every process, network peer, open file, and GPU a distributed MPI or training job touches, by hand or with the jobtrace.py script.

Why start from the job ID

When a distributed job is slow or stuck, the first question is not "what is wrong" but "what is this job touching." A job that spans ten nodes touches ten sets of processes, a web of network connections, a filesystem, and a set of GPUs. You cannot debug it until you can see all of that at once.

This is the method I use, the script that automates it, and the honest limits of both.

The manual method

Start from the Slurm job ID. Everything flows from it.

  1. Get the job. scontrol show job <id> gives you the nodes, the user, the state, and the start time. sacct -j <id> gives you the accounting: the CPU time, the memory, the exit code.
  2. Find the processes on each node. The job's processes are the MPI ranks. The reliable way to find them is to read /proc/<pid>/environ and look for SLURM_JOB_ID=<id>. That works regardless of how the cgroups are laid out, which varies between systems.
  3. Find the network peers. ss -tnp on each node, filtered by the rank PIDs, shows every TCP connection the rank has open: the peer IP and port, which is another rank, a storage server, or a metadata server. For InfiniBand, ibstat and ibdiagnet show the fabric links. For NCCL, set NCCL_DEBUG=INFO and read the log: it names the communicator, the ranks, and the transport it chose.
  4. Find the storage endpoints. lsof -p <pid> shows every open file descriptor: the files the rank has open, the sockets, and the pipes. The file paths tell you which filesystem the job is reading and writing. If lsof is not installed, ls -l /proc/<pid>/fd gives you the same information in a rawer form.
  5. Find the GPUs. nvidia-smi on each node shows which GPU each process is using, the GPU memory, and the utilization. Cross-check the PID from nvidia-smi against the rank PID from ps. If a rank is on the wrong GPU, or two ranks share one GPU, that is the problem.
  6. Find the syscalls, if it is stuck. strace -p <pid> shows the system calls in real time. A process stuck in read on a socket is waiting on the network. A process stuck in futex is waiting on a lock. A process making thousands of small read calls is doing small I/O.
  7. Build the map. The endpoints are: the other ranks (MPI peers), the storage (the filesystem and the metadata server), the scheduler (Slurm), the network (the fabric), and the GPUs. Write it as a list: rank 0 on node A talks to rank 1 on node B over the fabric, both read from the same filesystem, and both use GPU 0 on their node.

The tools, in order: scontrol and sacct for the job, ps for the processes, ss for the sockets, lsof for the files, nvidia-smi for the GPUs, ibstat for the fabric, strace for the syscalls, NCCL_DEBUG=INFO for the collectives.

The trap is starting with strace or tcpdump before you know which node and which PID to look at. The job ID is the entry point. Everything flows from it.

Automating it: Level 1, the on-demand script

Doing that by hand takes half an hour of SSH. The script does it in a minute.

jobtrace.py takes a Slurm job ID, gets the nodelist from scontrol, hits every node in parallel over SSH, and prints one map: rank to node to GPU to network peers to open files, plus a summary of the unique endpoints.

python3 jobtrace.py 12345
python3 jobtrace.py 12345 --json

How it works

  1. scontrol show job <id> gives the NodeList. A small expander turns node[001-004] into node001 through node004, including mixed forms like node[001-002,005] and multi-bracket forms like rack[1-2]node[01-02].
  2. On each node, in parallel over SSH, a small bash collector runs. It finds the job's PIDs by reading /proc/<pid>/environ for SLURM_JOB_ID=<id>, then collects ps, ss, lsof, and nvidia-smi. The collector reads the environ file with cat rather than a shell redirect, so a permission error on another user's process goes to cat's stderr (suppressed) instead of being reported by the shell.
  3. The results come back and are parsed into one report: for each node, each PID with its command line, its GPU, its network peers, and its open files. Then a summary of the unique endpoints: the network peers, the filesystems touched, and the GPUs in use.

What it needs

  • scontrol on the machine you run it from.
  • Passwordless SSH to the compute nodes (or ssh-agent).
  • No agent or daemon on the nodes.

What it does not do

It only sees what is running right now. After the job exits, the processes are gone and ss and lsof show nothing. So it is a diagnostic tool, not a record. If you want the map after the job finished, you need Level 2.

It is also untested end to end against a real Slurm job. The components are tested (the nodelist expander, the parser, the collector on a live process with SLURM_JOB_ID set), but the full path through scontrol and SSH to compute nodes has not been run on a real cluster yet. Run it against a live job first and check the output against a manual scontrol and ss on one node.

The script is jobtrace.py, in this repo's scripts/ folder.

Automating it: Level 2, the always-on platform

If you want the map available after the job finished, you need continuous collection. An agent on each node collects process, network, file, and GPU data, tags everything with the Slurm job ID (from the cgroup), and sends it to a central store. Then you can ask "show me job 12345" at any time.

The architecture is: an agent on the node, a collector in the middle, a time-series store for the metrics and a log store for the events, and a query service that returns the map for a job ID.

The hard parts are not the collection. They are:

  • Overhead. Tracing every syscall and every packet is expensive. eBPF helps because it runs in the kernel with low overhead, but you still have to be selective about what you capture.
  • Volume. A thousand-rank MPI job generates a huge amount of trace data. You need sampling or aggregation, not full capture.
  • Correlation. Linking a socket to a rank, a file to a process, and a GPU to a rank means joining data from the kernel, Slurm, and NVML. The job ID is the key, but not every data source has it.
  • Timing. The data has to be collected while the job runs. Continuous collection solves this, but it costs storage and CPU.
  • The application is a black box. MPI and NCCL do not emit traces by themselves. You can infer the endpoints from the kernel sockets, but you cannot tell if a connection is an all-reduce or a broadcast without the application's own logging (NCCL_DEBUG=INFO, or instrumenting with Score-P).

The tools that already do this

Before building Level 2, look at what exists. The question is build versus adopt.

  • Darshan is the HPC I/O tool. It intercepts the MPI-IO and POSIX calls and records exactly which files a job touched, how much it read and wrote, and the access pattern. That is the "which files" part, automated, and it is used at NERSC and ALCF.
  • Score-P and Vampir instrument MPI and OpenMP and produce a trace of the whole job, including the communication pattern. That is the "trace the MPI job" part, but it needs the application instrumented.
  • Nsight Systems (nsys) is the closest to end-to-end tracing for a GPU training job. nsys profile on the job gives you one timeline with the GPU kernels, the NCCL collectives, the MPI calls, and the OS events.
  • PyTorch Profiler does the same thing at the application level for PyTorch jobs: the kernels, the NCCL collectives, and the data loading, on a timeline.
  • Pixie uses eBPF to capture network traffic and process info automatically in Kubernetes, with no code changes. Same idea, different platform.
  • OpenTelemetry is the cloud-native standard for distributed tracing. You instrument the application to emit spans, and a collector aggregates them. It is built for microservices, not MPI, but the concept is the same.

The takeaway

Start with Level 1. It is a weekend project, it uses the tools you already know, and it is immediately useful the next time a job is slow. The full platform is a bigger build, and for the MPI and NCCL tracing part, Nsight Systems and Darshan already exist, so you would be adopting them rather than building from scratch.

And the method is the same at every level: start from the job ID, get the nodes and the PIDs, then ss for the network, lsof for the files, and nvidia-smi for the GPUs. The automation changes how fast you get the map. It does not change what the map is.

Examples are generic. Verify commands and defaults against your vendor and scheduler documentation before production use.
