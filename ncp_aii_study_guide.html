1. Exam at a glance

NCP-AII is a 120-minute, 70–75 question, remotely proctored exam ($400) that tests whether you can bring an NVIDIA AI cluster from bare racks to a burned-in, validated system. Two domains, bring-up (31%) and test/verification (33%), make up almost two-thirds of the score, so this tutorial spends most of its time there. Source: NVIDIA exam page

How to use this tutorial. Each domain section below follows the blueprint bullets in order. Every step has three parts: the concept to know, the commands to practise, and what "good" looks like. Work through the steps on real or cloud hardware where you can, and tick the checklist at the end of each domain. Where you already stand. As an HPC admin who runs Slurm, Rocky Linux, iLO/iDRAC automation and storage, you already cover much of Domains 3 and 5. The new ground is likely NVIDIA-specific: HGX firmware, NVLink/NVSwitch, InfiniBand/Spectrum-X fabric tools, BlueField, Base Command Manager and the burn-in tooling.

3. Build a practice lab

E. NVIDIA Academy courses Hosted labs: bring up an AI cluster with BCM; BlueField bring-up Fills gaps from tiers B–D

Steps to stage the lab

  1. Download the BCM 11 ISO and request the free license through the NVIDIA licensing portal.
  2. Create a lab network on your hypervisor: one internalnet (provisioning) and one externalnet, plus an optional ipminet if you emulate a BMC with vbmc (virtualbmc).
  3. Install the head node from the ISO (Section 6 below covers the wizard), then PXE-boot two empty VMs as compute nodes.
  4. Register at ngc.nvidia.com, generate an API key, and note it for the NGC CLI and nvcr.io pulls.
  5. Book GPU time in short, scripted bursts: keep a single lab.sh that installs drivers, toolkit and tests, so each paid session starts at the test, not the setup.
  6. Keep a lab notebook of every command and its output; the exam asks what output means, not just which command to run.

4. Domain 1: System and Server Bring-up (31%)

This domain is about taking a racked HGX/DGX node from "powered off" to "proven ready for workloads". Learn the order of operations cold; many questions are "what do you do next?"

Step 1.1 — Learn the deployment and validation sequence

Memorise this order; each stage gates the next.

  1. Site readiness: power circuits, PDUs, cooling capacity, floor loading, rack layout.
  2. Rack and stack: install nodes, switches, PDUs; label everything.
  3. Cable OOB first, then in-band management, storage fabric, compute (East-West) fabric.
  4. Power on and configure BMCs (IP, credentials, NTP, services).
  5. Baseline firmware on servers, GPU trays, NICs/DPUs, switches, transceivers.
  6. Provision the control plane (BCM head nodes, OS images, Slurm).
  7. Configure fabrics (UFM for InfiniBand, NetQ/Cumulus for Spectrum Ethernet).
  8. Single-node validation: nvidia-smi, DCGM diag, HPL, NCCL on NVLink.
  9. Multi-node validation: cable/BER checks, ClusterKit, NCCL across the fabric, storage tests.
  10. Burn-in (NCCL, HPL, NeMo), then hand over to users.

Step 1.2 — Understand AI-factory network topologies

An NVIDIA reference cluster has four separate networks. Know what each carries and why they are kept apart.

Network Typical tech Carries
Compute (East-West) InfiniBand NDR/XDR (Quantum) or Spectrum-X Ethernet, one 400G NIC per GPU GPU-to-GPU collective traffic (NCCL)
Storage (North-South) 200/400G Ethernet or IB, often via BlueField-3 Dataset reads, checkpoint writes
In-band management 100G/25G Ethernet Provisioning (PXE), SSH, Slurm, monitoring
Out-of-band (OOB) 1G Ethernet BMCs, switch management ports, PDUs

Key ideas the exam expects:

  • Rail-optimised fat-tree: GPU n in every node connects to leaf switch n of its scalable unit (SU). Same-rank GPUs talk through one switch hop, which suits NCCL rings and trees.
  • Non-blocking (1:1): leaf uplink bandwidth equals downlink bandwidth for the compute fabric.
  • Scalable unit: in DGX SuperPOD H100 designs an SU is 32 nodes; clusters scale by adding SUs and spine/core layers.
  • NVLink domain (inside a node, or across a rack on GB200 NVL72) is separate from the InfiniBand/Ethernet fabric.

Practise: draw a 2-SU rail-optimised fabric and count leaf and spine ports.

Step 1.3 — Configure BMC, OOB and TPM

  1. Give the BMC a static address and change default credentials:
ipmitool lan set 1 ipsrc static
ipmitool lan set 1 ipaddr 10.0.0.21
ipmitool lan set 1 netmask 255.255.255.0
ipmitool lan set 1 defgw ipaddr 10.0.0.1
ipmitool user list 1
ipmitool user set password 2 '<new-password>'
  1. Confirm Redfish works, since NVIDIA firmware tools use it:
curl -sk -u admin:<pw> https://<bmc-ip>/redfish/v1/Systems | jq
curl -sk -u admin:<pw> https://<bmc-ip>/redfish/v1/UpdateService/FirmwareInventory | jq
  1. Harden: set NTP and syslog targets, disable unused services (IPMI over LAN if Redfish-only), put BMCs on the isolated OOB network.
  2. TPM: enable TPM 2.0 in BIOS, then verify from the OS with tpm2_getcap properties-fixed and dmesg | grep -i tpm. Know that TPM backs Secure Boot measurements, disk-encryption keys and attestation.

Good looks like: BMC reachable only on OOB, non-default credentials, Redfish returns the system and firmware inventory.

Step 1.4 — Perform firmware upgrades (including HGX) and detect faults

On DGX/HGX H100/H200/B200 the tool is nvfwupd, which drives the BMC over Redfish. A system has two packages: a motherboard-tray package (BMC, BIOS, CPLD, PSU, NVMe) and a GPU-tray package (HGX: GPU VBIOS, NVSwitch, HMC, ERoT, FPGA). DGX H100 firmware update steps

  1. Compare installed versus packaged versions:
nvfwupd -t ip=<bmc> user=<u> password=<p> show_version \
  -p nvfw_DGX_<date>.fwpkg nvfw_DGX-HGX-H100-H200x8_<date>.fwpkg
  1. Update the BMC first, reset the BMC, then the rest of the motherboard tray:
nvfwupd -t ip=<bmc> user=<u> password=<p> update_fw -p <mb-tray>.fwpkg -y -s update_bmc.json
nvfwupd -t ip=<bmc> user=<u> password=<p> update_fw -p <mb-tray>.fwpkg -y -s mb_tray.json
  1. Update the GPU tray, then track the task:
nvfwupd -t ip=<bmc> user=<u> password=<p> update_fw -p <gpu-tray>.fwpkg -y -s gpu_tray.json
nvfwupd -t ip=<bmc> user=<u> password=<p> show_update_progress -i <task-id>
  1. Activate: most components need a BMC reset and/or an AC power cycle; read the release notes for the required activation and any intermediate ("transition") package.
  2. At cluster scale, BCM can drive nvfwupd across many nodes.

Fault detection sources: BMC System Event Log (ipmitool sel elist), Redfish event log, nvsm show health on DGX, nvidia-smi -q (retired pages, ECC), kernel dmesg Xid messages, and ERoT status in the firmware inventory.

Step 1.5 — Validate power and cooling parameters

  • Confirm PSU count, redundancy and input feeds; a DGX H100 draws up to about 10.2 kW, so check PDU circuits against nameplate power.
  • Read sensors:
ipmitool sdr type "Power Supply"
ipmitool sensor | grep -Ei 'inlet|temp|fan|pwr'
nvidia-smi -q -d POWER,TEMPERATURE,PERFORMANCE
  • Watch for HW Slowdown, HW Power Brake or HW Thermal Slowdown in the clocks-throttle reasons; any of these during a test means a power or cooling problem.
  • For liquid-cooled systems (GB200 NVL72), also check CDU flow, inlet coolant temperature and leak sensors.
  • Know nvidia-smi -pl <watts> (power cap) and that you should not cap GPUs during acceptance tests.

Step 1.6 — Install GPU-based servers and use nvidia-smi (SMI)

The "SMI" here is the NVIDIA System Management Interface. Commands to know cold:

nvidia-smi                      # summary
nvidia-smi -L                   # list GPUs and UUIDs
nvidia-smi topo -m              # GPU/NIC/CPU affinity matrix (NV#, PIX, PXB, SYS)
nvidia-smi nvlink --status      # per-link NVLink state and speed
nvidia-smi -q -d ECC,PAGE_RETIREMENT,ROW_REMAPPER
nvidia-smi -pm 1                # persistence mode (or run nvidia-persistenced)
systemctl status nvidia-fabricmanager   # needed on NVSwitch (HGX) systems

On HGX systems with NVSwitch, CUDA jobs fail until nvidia-fabricmanager is running and its version matches the driver.

Step 1.7 — Validate the installed hardware

Check that what the BOM says is what the OS sees:

lspci | grep -i nvidia | wc -l           # GPUs + NVSwitches
lspci -vvv -s <bdf> | grep -E 'LnkCap|LnkSta'   # PCIe gen and width match
nvidia-smi -L                             # expect 8 GPUs on HGX
ibstat ; ibv_devinfo                      # ConnectX/BlueField ports Active, rate 400
mst start ; mst status -v                 # Mellanox devices visible
nvsm show health                          # DGX only
dcgmi discovery -l                        # DCGM sees every GPU

A downgraded PCIe link (for example x8 instead of x16, or Gen4 instead of Gen5) is a classic finding.

Step 1.8 — Describe and validate cable types and transceivers

Type Reach Notes
DAC (passive copper) Up to ~2–3 m at 400G Cheapest, no power; within a rack
ACC/AEC (active copper) A little longer than DAC Signal conditioning in the connector
AOC (active optical cable) Tens of metres Fixed-length fibre with built-in optics
Transceiver + fibre Multimode SR (~50 m), single-mode DR/FR (500 m–2 km) MPO for parallel optics, LC duplex for FR; OSFP on NDR/XDR, QSFP112 on some NICs

On Quantum-2 switches, one twin-port OSFP cage carries 2 × 400G NDR ports. Validate with:

mlxlink -d <mst-dev> -m        # module type, vendor, part number, FW, temperature, power
mlxlink -d <mst-dev> -c        # counters: raw/effective BER, symbol errors
mlxcables                      # cable EEPROM details

Always inspect and clean fibre end-faces before seating optics; dirty connectors are the top cause of high BER.

Step 1.9 — Install physical GPUs

  • SXM (HGX): GPUs sit on the HGX baseboard; replacement is a field-service procedure with torque specs and thermal-interface handling. Follow the system service manual.
  • PCIe: place cards so each GPU shares a PCIe switch or CPU socket with its NIC (GPUDirect RDMA affinity); use correct auxiliary power cables; fit NVLink bridges where supported (for example H100 NVL pairs).
  • Always: ESD protection, power off and drain, record serial numbers, update the asset inventory.

Step 1.10 — Validate hardware operation for workloads

dcgmi diag -r 3                 # level 3: ~30 min, PCIe, memory, stress, NVLink checks
nvbandwidth                     # host-device and device-device bandwidth
lsmod | grep -E 'nvidia_peermem|nv_peer_mem'   # GPUDirect RDMA module loaded

Also confirm nvidia-smi topo -m shows each GPU paired with a NIC at PIX/PXB, not SYS.

Step 1.11 — Configure initial parameters for third-party storage

Certified storage partners include DDN, VAST, WEKA, NetApp, Pure and IBM Storage Scale. The initial work is client-side:

  1. Install the vendor client (Lustre/EXAScaler, WEKA, GPFS) or configure NFS over RDMA.
  2. Put storage traffic on the storage fabric, not the compute fabric; set MTU 9000 end to end on Ethernet.
  3. Tune mounts: for NFS use nconnect=16 and proto=rdma where supported.
  4. Enable GPUDirect Storage: install nvidia-fs, then check with /usr/local/cuda/gds/tools/gdscheck -p.
  5. Record baseline throughput with fio or gdsio (used again in Domain 4).

5. Domain 2: Physical Layer Management (5%)

Only about four questions, but both topics recur in Domains 3 and 4, so learn them properly once.

Step 2.1 — Configure and manage a BlueField network platform

Concepts. A BlueField-3 is a ConnectX-7 NIC plus Arm cores, memory and its own BMC. It runs in one of two main modes:

Mode What it means Typical use
DPU mode (default) Arm cores own the NIC; host traffic passes through the Arm's virtual switch (OVS/DOCA) Storage offload, security, multi-tenant isolation
NIC mode Arm cores out of the data path; behaves like a ConnectX NIC Simple high-speed NIC, East-West compute links on SuperNIC parts

Steps.

  1. Find the device and check firmware from the host:
mst start && mst status -v
flint -d /dev/mst/mt41692_pciconf0 q          # firmware version, PSID
mlxfwmanager --query
  1. Check or change the operating mode, then power-cycle the host:
mlxconfig -d /dev/mst/mt41692_pciconf0 q | grep -i INTERNAL_CPU
mlxconfig -d /dev/mst/mt41692_pciconf0 s INTERNAL_CPU_OFFLOAD_ENGINE=1   # NIC mode
mlxconfig -d /dev/mst/mt41692_pciconf0 s INTERNAL_CPU_OFFLOAD_ENGINE=0   # DPU mode
  1. Install the DPU OS (a BFB bundle containing Ubuntu, DOCA runtime and NIC firmware). Two routes:
    • From the host over RShim: install rshim, then bfb-install --bfb <bundle>.bfb --rshim rshim0.
    • From the DPU's BMC over Redfish (the method the study guide calls "BFB from BMC"), which needs no host OS.
  2. Reach the Arm OS over the RShim virtual Ethernet (tmfifo_net0, default 192.168.100.2) or the DPU's 1G OOB port; default user is ubuntu, and you set its password on first login.
  3. On the host, install DOCA-Host (the successor to MLNX_OFED) so the host has the right drivers and tools.
  4. Confirm: ibv_devinfo shows ports Active; on the DPU, ovs-vsctl show lists the bridges; bfvcheck reports component versions.

Step 2.2 — Configure MIG for AI and HPC

Concepts. Multi-Instance GPU splits one A100/A30/H100/H200/B200 into up to seven isolated instances, each with dedicated SMs, memory and L2 cache slices. A GPU instance (GI) owns memory; a compute instance (CI) inside it owns SMs. AI use: many small inference or notebook jobs. HPC use: fault and QoS isolation for many small jobs sharing a node. MIG instances cannot use NVLink peer-to-peer with each other.

Steps (H100 80GB example).

  1. Stop GPU clients (DCGM, persistence jobs), then enable MIG mode and reset:
nvidia-smi -i 0 -mig 1
nvidia-smi -i 0 -r            # or reboot if the reset is refused
  1. List the profiles the GPU offers:
nvidia-smi mig -lgip          # e.g. 1g.10gb, 2g.20gb, 3g.40gb, 4g.40gb, 7g.80gb
  1. Create GPU instances and their default compute instances in one go:
nvidia-smi mig -i 0 -cgi 3g.40gb,3g.40gb -C
nvidia-smi -L                 # each MIG device now has its own UUID
  1. Tear down in reverse order: nvidia-smi mig -dci then nvidia-smi mig -dgi, then nvidia-smi -i 0 -mig 0.
  2. Expose MIG to schedulers: in Slurm set AutoDetect=nvml in gres.conf so each MIG slice becomes a GRES; in Kubernetes the GPU Operator's MIG manager applies layouts with a single or mixed strategy. For repeatable layouts use nvidia-mig-parted with a YAML config.

6. Domain 3: Control Plane Installation and Configuration (19%)

This domain is NVIDIA Base Command Manager (BCM, formerly Bright Cluster Manager) plus the GPU software stack on each node. BCM 11 is the current release. Your Slurm background helps, but learn the BCM way of doing things: cmsh, categories, software images and cm-wlm-setup.

Step 3.1 — Install BCM, configure it, and verify HA

Install the primary head node.

  1. Boot the BCM ISO and run the graphical installer.
  2. Choose the network layout: Type 1 (compute nodes on a private internal network behind the head node) is the usual choice.
  3. Assign interfaces: externalnet (site), internalnet (provisioning, default 10.141.0.0/16), optionally ipminet (BMCs) and ibnet (InfiniBand).
  4. Pick the workload manager (or "None" and add Slurm later) and the base OS for the default software image.
  5. Install the license: request-license then install-license; check with verify-license.

Learn cmsh modes. Everything in BCM is an object you edit and then commit.

cmsh
% device                      # nodes, switches, PDUs
% category                    # groups of nodes sharing config
% softwareimage               # node OS images under /cm/images/
% network                     # internalnet, ibnet, ipminet
% wlm                         # Slurm clusters

Configure HA.

  1. Install a second head node with matching hardware and networks.
  2. On the primary, run cmha-setup and follow the wizard: choose the secondary, a shared (virtual) IP for failover, and shared storage for /cm/shared and /home (NAS or DRBD).
  3. Make sure BMC power control works for both heads; BCM uses it to fence (STONITH) a failed head.
  4. Verify and test:
cmha status                   # both heads, which is active, mysql/cmd/shared-IP checks
ssh head2 cmha makeactive     # manual failover
cmha status                   # confirm head2 is now active

Good looks like: every cmha status check passes on both heads, and Slurm's primary/backup controller follows the head pair.

Step 3.2 — Install the OS

  • Head nodes: from the BCM ISO (it lays down Ubuntu or RHEL/Rocky underneath).
  • Compute nodes: never installed by hand. They PXE-boot, run the BCM node-installer, and receive a full copy of their category's software image.
  • DGX nodes: use a DGX OS software image (Ubuntu-based with drivers, DCGM, NVSM preinstalled) imported into BCM.
  • Change an image with cm-chroot-sw-img /cm/images/<image>, then push changes to running nodes with imageupdate -w in cmsh device mode, or reboot them.

Step 3.3 — Install the cluster: categories, interfaces, Slurm, Enroot and Pyxis

Categories and nodes.

cmsh -c "category; clone default dgx; set softwareimage dgx-os-image; commit"
cmsh -c "device; add physicalnode dgx01 10.141.0.11; set category dgx; set mac <mac>; commit"

Interfaces (per node, or in a category for common settings):

cmsh
% device use dgx01
% interfaces
% add physical ibp24s0
% set network ibnet
% set ip 10.149.0.11
% commit

Know interface types: physical, bond, vlan, bridge, bmc. Then power on (power on -n dgx01) and watch it provision.

Slurm with Pyxis and Enroot.

  1. Run cm-wlm-setup, choose Setup (Step By Step), then Slurm.
  2. Put the server role on both head nodes (HA), and the client role on the GPU categories.
  3. GPU configuration: let Slurm auto-detect GPUs via NVML, or define 8 GPUs per node as GRES.
  4. Answer yes to "Configure Pyxis plugin?" so Enroot and Pyxis are installed into the images.
  5. Save the config (for example /root/cm-wlm-setup.conf) and deploy.
  6. If you add a new software image later, rerun cm-wlm-setup so that image also gets Pyxis/Enroot. NVIDIA BCM Slurm guide
  7. Validate:
module load slurm
sinfo                                   # nodes idle
srun -N1 --gpus=8 nvidia-smi -L         # 8 GPUs visible in a job
srun -N1 --gpus=8 --container-image=nvcr.io#nvidia/pytorch:<tag> \
     python -c "import torch; print(torch.cuda.device_count())"

Enroot specifics worth knowing: config in /etc/enroot/enroot.conf (ENROOT_RUNTIME_PATH, ENROOT_CACHE_PATH, ENROOT_DATA_PATH), NGC credentials in ~/.config/enroot/.credentials as machine nvcr.io login $oauthtoken password <API-key>, and the registry separator # in image names. Pyxis setup wiki

Step 3.4 — Install, update and remove NVIDIA GPU and DOCA drivers

GPU driver (on a bare host, or inside the software image chroot on BCM):

# Ubuntu example using NVIDIA's CUDA repo
apt install -y nvidia-driver-<branch>-server-open nvidia-fabricmanager-<branch>
# RHEL/Rocky example
dnf module install -y nvidia-driver:<branch>-open
systemctl enable --now nvidia-persistenced nvidia-fabricmanager
nvidia-smi                              # driver and CUDA version shown
  • Use the open kernel modules on current GPUs; Blackwell supports only the open modules.
  • Blacklist nouveau and rebuild the initramfs before the first install.
  • Update: install the new branch, keep fabric manager at the same version, reboot (or reprovision from the updated image).
  • Remove: apt purge '*nvidia*' or dnf module remove nvidia-driver, or run the .run installer with --uninstall if that is how it was installed.

DOCA-Host (replaces MLNX_OFED for ConnectX and BlueField hosts):

# after adding the DOCA repo for your distro
apt install -y doca-ofed        # or doca-all for the full SDK
/etc/init.d/openibd restart
ofed_info -s                    # version check
ibstat                          # ports Active

Remove with apt remove --purge doca-* (or ofed_uninstall.sh for a legacy MLNX_OFED install).

Step 3.5 — Install the NVIDIA Container Toolkit

# after adding the nvidia-container-toolkit repo
apt install -y nvidia-container-toolkit
nvidia-ctk runtime configure --runtime=docker      # edits /etc/docker/daemon.json
systemctl restart docker
nvidia-ctk cdi generate --output=/etc/cdi/nvidia.yaml   # optional CDI spec (Podman, containerd)

Step 3.6 — Use NVIDIA GPUs with Docker

docker run --rm --gpus all ubuntu nvidia-smi
docker run --rm --gpus '"device=0,1"' ubuntu nvidia-smi -L
docker run --rm --gpus all -e NVIDIA_DRIVER_CAPABILITIES=compute,utility <image>
docker login nvcr.io            # user: $oauthtoken  password: NGC API key
docker run --rm --gpus all --ipc=host --ulimit memlock=-1 \
  nvcr.io/nvidia/pytorch:<tag> python -c "import torch;print(torch.cuda.is_available())"

Know why --ipc=host (or a large --shm-size) matters for multi-GPU training: NCCL and PyTorch data loaders use shared memory.

Step 3.7 — Install the NGC CLI on hosts

  1. Download the Linux AMD64 or ARM64 zip from the NGC CLI installer page and unzip it.
  2. chmod u+x ngc-cli/ngc and add the folder to PATH.
  3. Run ngc config set and enter the API key, org, team and output format.
  4. Test: ngc registry image list nvidia/*pytorch* and ngc registry model list.

7. Domain 4: Cluster Test and Verification (33%)

The heaviest domain. Work through it in the same order you would on a real cluster: one node, then cables and firmware, then the fabric, then long burn-ins. For every test, know what a pass looks like and what a fail points to.

Stage Tests A failure usually means
Single node DCGM diag, HPL, NCCL on NVLink Bad GPU, NVSwitch/fabric manager issue, power or thermal throttling
Physical fabric mlxlink BER, ibdiagnet, cabling map, FW versions Dirty or bad optic, miswired port, mismatched firmware
Fabric performance ClusterKit, ib_write_bw, multi-node NCCL Slow link, wrong NIC/GPU affinity, routing or congestion settings
Endurance NCCL, HPL and NeMo burn-ins Intermittent faults that only show under hours of load
Storage fio, gdsio, IOR/mdtest Storage network, client config, or GDS not active

Step 4.1 — Single-node stress test

dcgmi diag -r 3                       # ~30 min; -r 4 adds longer stress and memory tests
nvidia-smi --query-gpu=index,temperature.gpu,power.draw,clocks.sm,clocks_throttle_reasons.active --format=csv -l 5

Pass: all DCGM plugins show Pass; during stress, clocks stay steady with no HW slowdown reasons. Also run nvsm stress-test on DGX systems.

Step 4.2 — Execute HPL

Use the NGC hpc-benchmarks container rather than building HPL yourself. NGC hpc-benchmarks

CONT='nvcr.io#nvidia/hpc-benchmarks:<tag>'
srun -N 1 --ntasks-per-node=8 --cpu-bind=none --mpi=pmix \
     --container-image="$CONT" --container-mounts=/path/to/dat:/my-dat \
     ./hpl.sh --dat /my-dat/HPL.dat
  • Sample input files live in /workspace/hpl-linux-x86_64/sample-dat/ inside the container; size N so the matrix fills most of GPU memory.
  • Know the HPL.dat parameters: N (problem size), NB (block size), P × Q (process grid = number of GPUs).
  • Pass: the residual check reads PASSED, and GFLOPS per GPU is consistent across nodes (an outlier node is your suspect).

Step 4.3 — Single-node NCCL and NVLink Switch verification

git clone https://github.com/NVIDIA/nccl-tests && cd nccl-tests
make MPI=1 MPI_HOME=/usr/mpi/gcc/openmpi CUDA_HOME=/usr/local/cuda
./build/all_reduce_perf -b 8 -e 16G -f 2 -g 8       # 8 GPUs, one process
  • Read the busbw column at large message sizes and compare it with NVIDIA's reference for your platform; H100/H200 SXM nodes typically reach several hundred GB/s.
  • NVSwitch checks: nvidia-smi nvlink --status (all links up at full speed), nvidia-smi -q | grep -A2 -i fabric (fabric state Completed, status Success), and systemctl status nvidia-fabricmanager.
  • Use NCCL_DEBUG=INFO to confirm NCCL is using NVLink (and NVLS, NVLink SHARP, where supported) rather than PCIe.

Step 4.4 — Validate cables by signal quality

mlxlink -d <dev> -c             # raw BER, effective BER, symbol errors, FEC
mlxlink -d <dev> -e             # eye opening per lane
ibdiagnet --get_phy_info --get_cable_info   # whole-fabric PHY and cable report

Pass: effective BER and symbol errors at zero or within spec, no lanes with poor eye opening, no links negotiated below NDR/XDR speed or below 4x width. Fail actions: clean fibre, reseat, then swap the optic, then the cable.

Step 4.5 — Confirm cabling is correct

Correct signal is not the same as correct wiring. A swapped rail cable passes BER checks but breaks rail optimisation.

  • InfiniBand: compare ibnetdiscover / iblinkinfo output with the planned topology; UFM's cable validation feature does this against a topology file.
  • Ethernet: compare LLDP neighbours (lldpctl, or NetQ) with the cabling plan.
  • Check that GPU n of every node lands on rail n.

Step 4.6 — Confirm switch firmware and software

ibswitches                       # all switches discovered
flint -d lid-<switch-lid> q      # in-band firmware query of an IB switch
# on a Quantum switch (MLNX-OS CLI)
show version
# on Spectrum with Cumulus Linux
nv show system

Pass: every switch on the same approved firmware/OS version from the release matrix.

Step 4.7 — Confirm BlueField-3 firmware and software

  • From the host: flint -d /dev/mst/mt41692_pciconf0 q and mlxfwmanager --query.
  • On the DPU Arm OS: bfvcheck (BFB, ATF, UEFI, NIC firmware) and cat /etc/mlnx-release.
  • DPU BMC firmware via its Redfish FirmwareInventory.
  • Confirm the mode (DPU or NIC) matches the design.

Step 4.8 — Confirm transceiver firmware

mlxlink -d <dev> -m reports the module's vendor, part number and firmware version; on switches use the transceiver show commands. LinkX optics firmware can be updated with the flint/mlxfwmanager LinkX options; follow the release notes for the approved version.

Step 4.9 — Run ClusterKit for a multifaceted node assessment

ClusterKit ships in the HPC-X toolkit. It tests latency, bandwidth, memory bandwidth, collectives, GPU-to-GPU and GPU-to-host paths, and bisection bandwidth, and needs Slurm or passwordless SSH across hosts. HPC-X ClusterKit docs

source <hpcx>/hpcx-init.sh && hpcx_load
$HPCX_CLUSTERKIT_DIR/bin/clusterkit.sh -f hostfile.txt \
  --hca_list "mlx5_0:1,mlx5_1:1" --ppn 1 -g
  • Install HPC-X on a shared directory so every node sees the same files.
  • Pairwise tests need at least two nodes.
  • Read the output heat maps: a row and column of poor results crossing at one node identifies a slow node; a single cold cell identifies a slow link.

Step 4.10 — Verify East-West fabric bandwidth with NCCL

# first a point-to-point sanity check (perftest)
ib_write_bw -d mlx5_0 --report_gbits                 # on node A
ib_write_bw -d mlx5_0 --report_gbits <nodeA>         # on node B
ib_write_bw -d mlx5_0 --use_cuda=0 --report_gbits <nodeA>   # GPUDirect RDMA path

# then NCCL across nodes, one rank per GPU
srun -N 2 --ntasks-per-node=8 --gpus-per-node=8 --mpi=pmix \
     ./build/all_reduce_perf -b 8 -e 16G -f 2 -g 1
  • Expect each 400G NDR link near line rate (~390 Gb/s) in ib_write_bw.
  • Scale NCCL from 2 nodes to an SU to the full cluster; busbw should stay roughly flat. A drop at one scale points to a spine or routing issue.
  • Useful variables: NCCL_DEBUG=INFO, NCCL_IB_HCA, NCCL_SOCKET_IFNAME, NCCL_ALGO.

Step 4.11 — NCCL burn-in

Run all_reduce (and all_to_all) across the full cluster for hours, for example in a loop or with a high iteration count (-n). Watch for busbw dips, new Xid errors in dmesg, rising IB port error counters, and link flaps in UFM.

Step 4.12 — HPL burn-in

Repeat full-cluster HPL runs over many hours (overnight is common). Pass: every run's residual PASSED and GFLOPS varies only a few percent between runs. HPL stresses power and cooling hardest, so it exposes weak PSUs and hot spots.

Step 4.13 — NeMo burn-in

Run a real training workload: a NeMo Framework pretraining recipe (for example a GPT- or Llama-style model on synthetic or mock data) across the whole cluster for several hours. Monitor step time, tokens per second and loss. It catches problems synthetic tests miss: storage stalls during checkpoints, rare NCCL timeouts and memory errors under mixed load.

Step 4.14 — Test storage

fio --name=seqread --rw=read --bs=1M --size=20G --numjobs=16 --direct=1 --directory=/mnt/data
/usr/local/cuda/gds/tools/gdsio -f /mnt/data/test -d 0 -w 8 -s 10G -i 1M -x 0 -I 0   # GDS read
mpirun -np <N> ior -w -r -t 1m -b 16g -F -o /mnt/data/ior   # aggregate parallel I/O

Compare per-node and aggregate results with the vendor's sizing and with the baseline from Step 1.11. Test metadata (mdtest) and checkpoint write time too.

Domain 4 checklist

8. Domain 5: Troubleshoot and Optimize (12%)

Expect scenario questions: "a node shows X, what is the most likely cause and the next step?" The safe answer pattern is isolate, gather evidence, replace the smallest part, re-validate.

Step 5.1 — Identify and troubleshoot hardware faults (GPU, fan, network card)

Evidence sources, in order of use:

dmesg -T | grep -i xid                  # GPU Xid events
nvidia-smi -q -d ECC,PAGE_RETIREMENT,ROW_REMAPPER
dcgmi health -s a && dcgmi health -c    # enable all watches, then check
ipmitool sel elist                      # fans, PSUs, temperatures from the BMC
ipmitool sdr | grep -Ei 'fan|psu|temp'
nvsm show health                        # DGX
nvidia-bug-report.sh                    # support bundle for NVIDIA
ibstat; ibqueryerrors; perfquery        # NIC and port counters

Xid codes worth memorising:

Xid Meaning Usual action
13, 31, 43 Graphics exception, MMU fault, GPU stopped processing Usually the application; rerun, check code, then DCGM diag
48 Double-bit ECC error Reset GPU; repeated events mean RMA
63, 64 ECC page retirement or row-remap event / failure Reset to apply remap; a failure means RMA
74 NVLink error Check NVLink status and fabric manager; reseat or service
79 GPU has fallen off the bus Hardware or power; drain node, check PCIe, PSU, seating
92, 94, 95 High single-bit ECC rate, contained / uncontained ECC Drain, reset, run DCGM diag; RMA if it repeats

Fans and PSUs show up in the BMC SEL and sensor readings first; a failed fan often appears as GPU thermal slowdown before anything else. NIC faults appear as ports down, degraded width/speed, or climbing symbol and link-recovery counters.

Step 5.2 — Identify faulty cards, GPUs and power supplies

  • Map the logical device to the physical slot: nvidia-smi -q (serial, PCI bus ID, module ID), lspci -vvv, ipmitool fru, and the system's slot diagram.
  • Turn on the locate LED: ipmitool chassis identify 240.
  • Distinguish a bad part from a bad slot or cable by swapping one variable at a time.

Step 5.3 — Replace faulty cards, GPUs and power supplies

  1. Drain the node: scontrol update nodename=<n> state=drain reason="GPU3 Xid79" (or close it in BCM).
  2. Power off; PSUs in a redundant set can usually be hot-swapped, GPUs and NICs cannot.
  3. Replace per the service manual (ESD, torque, thermal pads).
  4. Bring the new part to the cluster's firmware baseline (Step 1.4).
  5. For a new ConnectX/BlueField: GUIDs and MACs change, so update BCM interface records, UFM, and any partition (PKey) membership.
  6. Re-validate: dcgmi diag -r 3, single-node NCCL, then a short multi-node NCCL run.
  7. Resume: scontrol update nodename=<n> state=resume, and record the RMA.

Step 5.4 — Optimise performance on AMD and Intel servers

Area AMD EPYC Intel Xeon
NUMA Set NPS (NUMA nodes per socket) as the platform guide recommends, often NPS1 for GPU servers Sub-NUMA Clustering usually off for GPU servers
Power Performance determinism, max power profile, limit deep C-states Performance power profile, Energy Perf Bias = performance, limit deep C-states
I/O IOMMU in passthrough (iommu=pt), max xGMI link width/speed, Preferred I/O for GPU/NIC root ports VT-d with intel_iommu=on iommu=pt
Both PCIe ACS disabled on switches in the GPU-NIC path so peer-to-peer and GPUDirect RDMA work; PCIe max read request 4096; Relaxed Ordering enabled Same

OS-level tuning on both:

cpupower frequency-set -g performance      # or tuned-adm profile throughput-performance
nvidia-smi topo -m                         # read CPU and NUMA affinity per GPU
srun --cpu-bind=cores --gpus-per-task=1 ...   # bind ranks to the GPU's NUMA node

Always follow the server vendor's and NVIDIA's platform tuning guide; the exam favours "check the recommended BIOS settings" over guessing.

Step 5.5 — Optimise storage

  • Turn on GPUDirect Storage so data moves NIC-to-GPU without a CPU bounce buffer.
  • Keep storage traffic on its own fabric, with RDMA and MTU 9000.
  • Use multiple client connections (nconnect) and multiple NICs.
  • Use local NVMe (/raid on DGX) as a cache, for example FS-Cache for NFS, or a staging area for datasets.
  • On parallel file systems, stripe large files across targets (Lustre lfs setstripe).
  • Size for checkpoints: write bandwidth must absorb the full model checkpoint within the target window.

9. Exam-day strategy and self-check questions

With 120 minutes for up to 75 questions you have about 1.6 minutes each, so answer what you know on the first pass, flag the rest, and come back.

Strategy.

  • Test your webcam, ID and room setup for remote proctoring the day before.
  • Read for the stage the question is in (bring-up, validation, troubleshooting); the right answer is usually the next step in the sequence, not the most powerful tool.
  • Prefer non-destructive, evidence-first answers: check logs and counters before replacing parts.
  • Watch for "single-node" versus "multi-node" wording; it decides between NVLink tests and fabric tests.
  • Eliminate answers that skip validation after a change.

Self-check questions (answer before reading the answer line).

  1. A new HGX H100 node reports CUDA initialisation errors, but nvidia-smi lists all 8 GPUs. What do you check first?
    • nvidia-fabricmanager: running, and the same version as the driver.
  2. Two nodes pass mlxlink BER checks, but multi-node NCCL is slow only between rails 3 and 4. Likely cause?
    • Swapped cables between rails; verify cabling against the topology (Step 4.5).
  3. Which tool updates both the motherboard tray and the HGX GPU tray through the BMC?
    • nvfwupd, using the motherboard-tray and GPU-tray .fwpkg files.
  4. What must you run again after adding a new software image to a BCM cluster that already has Slurm with Pyxis?
    • cm-wlm-setup, so the new image gets the Pyxis, Enroot and CMDaemon packages.
  5. Which command fails over the BCM head nodes manually?
    • cmha makeactive on the passive head; check with cmha status.
  6. You need seven isolated inference slices on one H100. What do you create?
    • Seven 1g.10gb MIG GPU instances with compute instances (-cgi with -C).
  7. How do you switch a BlueField-3 to NIC mode?
    • mlxconfig ... s INTERNAL_CPU_OFFLOAD_ENGINE=1, then a host power cycle.
  8. Which column of nccl-tests output do you compare against reference values?
    • busbw (bus bandwidth), at large message sizes.
  9. ClusterKit shows one row and column of poor bandwidth crossing at node17. What does that mean?
    • node17 is slow with every peer: suspect its NIC, cable, PCIe link or affinity.
  10. A GPU logs Xid 79. First actions?
    • Drain the node, check PCIe link, power and seating, collect nvidia-bug-report.sh; likely hardware.
  11. Which burn-in best exposes power and cooling weaknesses?
    • HPL burn-in.
  12. What proves GPUDirect Storage is active on a client?
    • gdscheck -p shows GDS supported for the file system, and gdsio reaches expected throughput.
  13. After replacing a ConnectX card, which records must you update?
    • BCM interface MAC/GUID, UFM, and any InfiniBand partition (PKey) membership.
  14. On an AMD GPU server, which BIOS settings matter most for GPU-NIC peer-to-peer?
    • IOMMU passthrough, ACS disabled in the GPU-NIC path, the platform's recommended NPS and Preferred I/O settings.
