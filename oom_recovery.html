After an OOM Kill: Reboot or Not?

How to tell whether a Linux node recovered cleanly from an out-of-memory event, and how to keep cluster nodes from getting there.

Short answer

Usually no reboot is needed. The OOM killer exists so the kernel can survive memory exhaustion by killing a process. Once the victim dies and its memory is freed, the kernel is back in a normal state. An OOM kill does not taint the kernel or make it unstable on its own.

The real question is whether the system recovered cleanly, and that depends on what happened during and after the event.

Cgroup OOM vs. global OOM

  • Cgroup OOM: for example, a Slurm job hitting its --mem limit under cgroup enforcement. This is routine. Only that job's cgroup was affected, and the node is fine.
  • Global OOM: the whole machine ran out of memory. Worth a closer look, because the killer may have picked something you care about, and the node may have thrashed badly before it fired.

What to check after a global OOM

  1. What got killed. Run dmesg -T | grep -i -A20 "out of memory" or journalctl -k. If it was a daemon such as sshd, slurmd, munged, sssd, systemd-journald, dbus, or nfsd, the node may look up but be broken for its purpose. Check systemctl --failed and restart what's needed.
  2. Whether the memory consumer is actually gone. If something keeps respawning (a runaway service, or a user process restarted by a wrapper), you'll just OOM again.
  3. Processes stuck in D state. Run ps -eo stat,pid,cmd | grep '^D'. Hung tasks, often on NFS or storage I/O that stalled under memory pressure, can't be killed. They are a common reason a reboot ends up being the practical fix.
  4. Kernel-side memory. Check SUnreclaim in /proc/meminfo and run slabtop. If unreclaimable slab is huge and not shrinking, you have a kernel or driver leak. Killing user processes can't fix that, so reboot and investigate the driver or module.
  5. Kernel errors beyond the OOM itself. A BUG, oops, soft or hard lockup, hung_task warnings, or filesystem errors (XFS shutdown, ext4 remounted read-only) mean you should reboot.
  6. Fragmentation. Repeated page allocation failure: order:N messages despite plenty of free memory can persist. Try echo 1 > /proc/sys/vm/compact_memory first; a reboot clears it if that doesn't help.

Rule of thumb

  • The right victim was killed, critical services are up, there are no D-state hangs or kernel stack traces, and slab looks normal: leave it running.
  • Any of those is off, or you can't confidently verify the node's state: reboot. On compute nodes especially, draining and rebooting is cheap insurance compared with jobs landing on a half-broken node.

Prevention on cluster nodes

  • Protect key daemons with OOMScoreAdjust=-1000 in their systemd units (sshd, slurmd, munge). Then confirm job processes don't inherit that value: check /proc/<pid>/oom_score_adj on a running job task. If they do, the OOM killer can't pick the job and will go after something else.
  • Enforce memory through Slurm cgroups (ConstrainRAMSpace=yes in cgroup.conf) so jobs OOM inside their own cgroup instead of taking down the node.
  • Reserve memory for the OS with MemSpecLimit on the node definition, or a systemd slice limit for user sessions on login nodes.
  • Optional policy: some sites set vm.panic_on_oom=1 with kernel.panic=10 on compute nodes, so a global OOM becomes an automatic reboot instead of a node in an unknown state. That's a legitimate choice if you'd rather have clean reboots than manual triage.
