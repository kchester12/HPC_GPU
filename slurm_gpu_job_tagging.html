Slurm GPU Job Tagging Hooks

Two non-blocking PrologSlurmctld and EpilogSlurmctld scripts that post GPU allocation and release events to a metrics API, plus how to deploy them alongside an existing prolog.

What these do

Two lightweight controller-side scripts tell a metrics API when a job gets GPUs and when it gives them back. Dashboards and cost reports can then tie GPU metrics to jobs without adding job labels to every infrastructure metric.

They are deliberately non-blocking: a tagging failure is logged and ignored, so it never delays job launch or completion.

This is the controller-side companion to section 8 of the GPU and RDMA observability design.

Controller side vs. node side. slurmctld runs these on the controller, which usually has no GPUs and can't run nvidia-smi. SLURM_JOB_GPUS gives GPU indices, and for a multi-node job those indices don't say which node they belong to. Use these hooks for job-level start and end events. For per-node GPU UUID mapping, use a node-side Prolog, which runs on each allocated node and can see the hardware.

Prolog: tag GPUs at job start

#!/usr/bin/env python3
"""Slurm PrologSlurmctld: tag GPUs allocated to a job at launch."""
import json, os, signal, sys, time, urllib.request

TAG_API = os.environ.get("GPU_TAG_API", "http://metrics-api:8080/gpu-tags")
TIMEOUT = 2.0        # per network operation
HARD_LIMIT = 3       # whole script, in seconds; also covers slow DNS

def give_up(*_):
    print("gpu tag: timed out", file=sys.stderr)
    sys.exit(0)

def main():
    signal.signal(signal.SIGALRM, give_up)
    signal.alarm(HARD_LIMIT)

    job_id = os.environ.get("SLURM_JOB_ID")
    if not job_id:
        sys.exit(0)  # not a job context
    gpus = [g.strip() for g in os.environ.get("SLURM_JOB_GPUS", "").split(",") if g.strip()]
    payload = {
        "event": "job_start",
        "job_id": job_id,
        "user": os.environ.get("SLURM_JOB_USER"),
        "partition": os.environ.get("SLURM_JOB_PARTITION"),
        "nodes": os.environ.get("SLURM_JOB_NODELIST"),
        "gpus": gpus,
        "start_ts_ms": int(time.time() * 1000),
    }
    req = urllib.request.Request(TAG_API, data=json.dumps(payload).encode(),
                                 headers={"Content-Type": "application/json"},
                                 method="POST")
    try:
        urllib.request.urlopen(req, timeout=TIMEOUT)
    except Exception as e:
        print(f"gpu tag failed: {e}", file=sys.stderr)  # never block launch
    sys.exit(0)

if __name__ == "__main__":
    main()

Epilog: release the tag at job end

#!/usr/bin/env python3
"""Slurm EpilogSlurmctld: close the GPU tag when the job ends."""
import json, os, signal, sys, time, urllib.request

TAG_API = os.environ.get("GPU_TAG_API", "http://metrics-api:8080/gpu-tags")
TIMEOUT = 2.0
HARD_LIMIT = 3

def give_up(*_):
    print("gpu untag: timed out", file=sys.stderr)
    sys.exit(0)

def main():
    signal.signal(signal.SIGALRM, give_up)
    signal.alarm(HARD_LIMIT)

    job_id = os.environ.get("SLURM_JOB_ID")
    if not job_id:
        sys.exit(0)
    gpus = [g.strip() for g in os.environ.get("SLURM_JOB_GPUS", "").split(",") if g.strip()]
    payload = {
        "event": "job_end",
        "job_id": job_id,
        "gpus": gpus,
        "exit_code": os.environ.get("SLURM_JOB_EXIT_CODE"),
        "end_ts_ms": int(time.time() * 1000),
    }
    req = urllib.request.Request(TAG_API, data=json.dumps(payload).encode(),
                                 headers={"Content-Type": "application/json"},
                                 method="POST")
    try:
        urllib.request.urlopen(req, timeout=TIMEOUT)
    except Exception as e:
        print(f"gpu untag failed: {e}", file=sys.stderr)
    sys.exit(0)

if __name__ == "__main__":
    main()

Why the extra timer

urlopen(timeout=...) limits each socket operation, but not DNS lookup. If the API's hostname stops resolving, a plain urlopen can hang well past two seconds, and slurmctld waits for PrologSlurmctld before launching the job. The SIGALRM limit caps the whole script, so the worst case is a three-second delay, never a stuck launch.

Deploying

  1. Save the scripts as /etc/slurm/prolog_gpu_tag.py and /etc/slurm/epilog_gpu_tag.py.
  2. Make them executable and readable by the user slurmctld runs as (SlurmUser, usually slurm): chmod 755.
  3. Confirm the controller can reach the API: curl -s -o /dev/null -w '%{http_code}\n' http://metrics-api:8080/gpu-tags.

  4. Add to slurm.conf:

    PrologSlurmctld=/etc/slurm/prolog_gpu_tag.py
EpilogSlurmctld=/etc/slurm/epilog_gpu_tag.py

  5. Run scontrol reconfigure, then test with a short job: salloc --gres=gpu:1 sleep 30. Check the API received both events, and check slurmctld.log for "gpu tag failed" lines.

PrologFlags=Alloc isn't needed for these. It changes when the node-side Prolog runs, not PrologSlurmctld.

If you already have a PrologSlurmctld

Older Slurm releases accept only one script per hook. Newer releases accept a comma-separated list or a glob (for example, a prolog.d/* directory) for some hooks; check the slurm.conf man page for your version. A small wrapper works on every version and keeps concerns separate:

#!/bin/bash
# /etc/slurm/prolog_slurmctld_wrapper.sh
set -euo pipefail

# Existing logic: a non-zero exit here still fails the prolog, as before
/etc/slurm/your_existing_prolog.sh "$@"

# GPU tagger: never allowed to fail the job, even if the file is missing
/etc/slurm/prolog_gpu_tag.py "$@" || true

Make a matching epilog_slurmctld_wrapper.sh, then point slurm.conf at the wrappers:

PrologSlurmctld=/etc/slurm/prolog_slurmctld_wrapper.sh
EpilogSlurmctld=/etc/slurm/epilog_slurmctld_wrapper.sh

The || true matters. Under set -e, a missing or broken tagger would otherwise make PrologSlurmctld exit non-zero, and Slurm requeues or holds the job: exactly the outage these scripts are designed to avoid.

Examples are generic. Verify commands and defaults against your vendor and scheduler documentation before production use.
